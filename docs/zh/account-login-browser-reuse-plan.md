# 自动登录队列浏览器复用优化方案

日期：2026-10-18

状态：代码已实现，待生产试运行。本文保留设计与验收基线；当前配置及运维方式见 [自动登录与会话恢复部署](account-auto-login-operations.md)。

## 1. 背景与目标

公益站账号池中的许多 Workspace 子账号在同一时期导入，会话也可能集中失效，形成连续的自动登录任务。当前实现每次尝试都启动并销毁独立 Camoufox，批量恢复期间会反复支付浏览器启动和退出成本。

本次采用折中方案：**独立登录浏览器在连续任务之间复用，每次尝试创建全新 Context；队列空闲后关闭浏览器。** 登录浏览器继续与请求浏览器、VNC 分离。

主要目标：

- 减少批量恢复期间的浏览器启动次数和累计 CPU 消耗。
- 通过尽早释放登录页面，降低验证阶段的资源峰值。
- 保留登录异常时终止整个独立执行器的能力，避免影响请求服务。
- 提供可对照的运行指标与回滚方式，观察实际服务器压力后再决定是否进一步优化。

本方案不能消除页面加载、脚本执行及目标服务验证的成本，也不预设能够额外增加多少请求 Context。浏览器空闲保留期间会继续占用基础内存，收益须通过运行数据确认。

## 2. 当前实现与改动范围

相关文件：

| 文件                                                | 当前职责                                             | 预期调整                                       |
| --------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| `src/accounts/AccountLoginQueue.js`                 | 每次尝试 fork 独立执行器，监督期限、截图与进程组终止 | 管理可复用执行槽、执行器生命周期和故障隔离     |
| `src/accounts/AccountLoginWorker.js`                | 启动浏览器、执行单次登录、验证及关闭资源             | 分离浏览器资源与尝试资源，支持顺序接收多次任务 |
| `src/accounts/TargetSessionValidator.js`            | 使用传入浏览器创建验证 Context 和临时验证连接        | 明确清理 Context、连接、定时器及临时代理的责任 |

| `src/config/ConfigurationService.js` 及关联配置定义 | 统一配置管理                                         | 按现有配置体系接入新增参数                     |
| `src/accounts/AccountLoginService.js`               | 任务持久化、版本校验和会话提交                       | 保留现有提交约束，适配执行器归属记录           |

当前 `finish()` 无论成功失败都会终止执行器进程组；Worker 的 `close()` 会关闭浏览器，且仅接受一次任务。因此不能仅缓存 browser 变量，需要同时修改监督协议和清理边界。

本次不调整请求 Context 池容量、账号调度规则、登录交互节奏、Google 验证处理方式或成功验证标准。本方案参数已接入统一配置体系，浏览器复用默认关闭，需在统一配置页或首次部署环境中显式开启。

## 3. 执行结构

每个登录并发槽拥有一个独立、可复用的 Worker 进程和一个 Camoufox。槽内串行执行，不允许同一个浏览器同时承接多个账号尝试。

```text
AccountLoginQueue
├─ 登录槽 1：独立进程组
│  └─ Worker + Camoufox
│     ├─ 尝试 A：新建 Context → 登录与验证 → 完整清理
│     └─ 尝试 B：新建 Context → 登录与验证 → 完整清理
└─ 登录槽 2…N：仅在配置并发大于 1 时创建

请求浏览器、请求 Context 池、VNC 保持独立
```

默认并发继续为 1。已有并发大于 1 的配置不得被静默改写；各槽独立复用。槽按需创建，不在服务启动时预热全部登录浏览器。

同一个任务重试时也创建全新 Context，不保留前一次登录页面或半成品会话。重试等待不占用执行槽，浏览器可供其他就绪任务使用。

## 4. 浏览器与任务生命周期

### 4.1 执行槽状态

| 状态          | 含义                             | 是否可领取任务 |
| ------------- | -------------------------------- | -------------- |
| `STOPPED`     | 没有存活的执行器和浏览器         | 可按需启动     |
| `STARTING`    | 正在启动执行器或浏览器           | 否             |
| `BUSY`        | 正在执行一次登录尝试             | 否             |
| `CLEANING`    | 正在清理该尝试的资源             | 否             |
| `IDLE`        | 浏览器健康，且前一尝试已完整清理 | 是             |
| `RETIRING`    | 正在关闭执行器和浏览器           | 否             |
| `QUARANTINED` | 无法确认进程或资源已回收         | 否             |

生命周期转换由队列统一管理。空闲回收、任务领取、取消和完成事件必须串行协调，防止一个槽同时被复用和关闭。

### 4.2 正常执行

1. 队列按原有规则选择到期、可执行的任务，并固定账号、凭据版本、会话版本和尝试令牌。
2. 优先使用健康空闲槽；没有可用槽且未达到并发上限时，创建执行器和浏览器。
3. 冷启动计入本次尝试总时限，沿用现有尝试次数和整轮恢复期限语义。
4. 为本次尝试创建全新登录 Context，应用该账号的代理和原有登录参数。
5. 完成 Google 登录、AI Studio 检查、目标服务初始化和最终身份及弹窗复查。
6. 获取最终 `storageState`，清理本次尝试全部资源。
7. 管理进程确认结果有效且资源清理完成后，按原有提交边界校验账号与版本并提交会话。
8. 浏览器符合复用条件时，执行槽进入 `IDLE`；否则进入重建流程。

Worker 可先上报待提交结果，但该消息不代表槽已空闲，也不代表账号恢复成功。必须有独立、明确的清理完成确认；不得通过收到成功结果立即释放槽。

### 4.3 空闲关闭

拟定空闲保留时间为 60 秒，从执行槽确认清理完成并进入 `IDLE` 时起算。

- 已有就绪任务时立即复用，不人为等待 60 秒。
- 只有未来到期的重试任务时，正常启动空闲回收计时，不为远期任务无限保活。
- 领取新任务时撤销对应槽的空闲定时器；定时器回调必须核对槽状态与执行器代次。
- 队列暂停时，运行中的任务按原规则完成；空闲浏览器仍在保留期结束后退出。
- 空闲关闭只销毁执行器资源，不修改任务状态、账号状态或尝试次数。

### 4.4 周期重建

首轮观察建议每个浏览器最多承接 20 次尝试，或存活 30 分钟，任一达到后在当前尝试清理完成时退出。成功和失败尝试均计数。

达到上限不打断运行中的任务。存在后续任务时创建新执行器继续消费；周期退出不计为账号登录失败，也不增加账号尝试次数。

上述数值是初始运营参数，不是已验证的最优值。暂不增加依赖浏览器内部私有接口的内存检测和自动重建逻辑。

## 5. 资源隔离与页面峰值优化

### 5.1 每次尝试必须隔离的状态

- 新建 Context，不复用前一账号 Cookie、localStorage、页面或登录缓存。
- 尝试令牌、截止时间、取消标记、诊断内容、截图锁、敏感值遮罩集合必须重置。
- `LoginInteraction`、页面处理器、验证器、监听器和定时器均归属当前尝试。
- 目标验证继续使用独立临时代理、临时端口和独立 `ConnectionRegistry`，不进入正式请求连接池。
- 代理在 Context 层按账号配置，验证流量继续沿用该账号出口。不得因浏览器复用沿用前一个账号的出口。

浏览器级设置必须保持与现有独立登录浏览器一致。若以后出现必须改变浏览器级配置的情况，先重建浏览器，再领取相应任务。

### 5.2 减少 Context 和页面重叠

当前流程会在原登录 Context 尚未关闭时创建目标验证 Context。优化后：

1. 初次 AI Studio 检查完成后，导出用于验证的 `storageState`。
2. 关闭原登录 Context，确认回收后再创建目标验证 Context。
3. 在目标验证 Context 内完成必要的最终身份和条款检查，结束后统一清理页面与连接。

原登录 Context 无法关闭时，不继续创建验证 Context，以免叠加资源。诊断截图应跟随当前有效页面，必要时在关闭前采集；不得为了保留截图页面而长期维持旧 Context。

目标服务验证所需的内部 iframe、连接页面等不机械压缩为单页；优化不得破坏真实 WebSocket 握手和最终会话检查。

### 5.3 清理确认

进入 `IDLE` 前必须确认本次创建的所有 Context 已关闭，并清理临时代理、WebSocket、监听器、定时器及凭据引用。

目前验证器的 `close()` 主要负责传输和部分定时器；实施时须审计初始化失败、尚未返回 Context、页面创建中途失败等分支。通过执行器级尝试资源登记表追踪资源，不得仅清理最终返回的 Context。

正常复用路径不调用 `browser.close()`；整个执行器退出时才关闭浏览器。若无法证明尝试资源已完整回收，不复用该浏览器。

## 6. 监督协议、超时与故障处理

### 6.1 区分执行器与尝试

引入稳定的执行器 ID 或代次，以及每次尝试独立的令牌。所有任务消息至少携带执行器代次、任务 ID 和尝试令牌；管理进程和 Worker 均校验归属。

协议应区分执行器就绪、阶段进度、待提交结果、截图、清理完成、浏览器断连和执行器退出。旧任务迟到结果、旧清理确认和旧空闲定时器不得影响新任务。

Worker 同一时间只接受一个尝试。忙碌期间收到另一执行命令应报告协议错误，不能覆盖当前任务；两次正常尝试之间必须重建所有尝试级状态。

### 6.2 失败分类与复用策略

| 情况                                         | 浏览器处理           | 任务处理                     |
| -------------------------------------------- | -------------------- | ---------------------------- |
| 登录成功，资源清理完整                       | 可复用               | 按原有校验提交会话           |
| 密码错误、人工挑战等业务失败，资源清理完整   | 可复用               | 保留原有错误分类和重试策略   |
| 尝试总超时或运行中取消                       | 退出整个执行器       | 撤销令牌，按原规则记录或重试 |
| 浏览器断连、协议异常、Context 创建或关闭卡住 | 退出整个执行器       | 按原规则归类故障，不盲目复用 |
| 执行器进程组无法确认已退出                   | 隔离槽并继续监督回收 | 不启动替代执行器绕过故障容量 |

超时和取消首版继续使用“有界诊断与清理后终止专属进程组”的保守策略。异常时牺牲浏览器复用收益，保留当前可靠的回收边界。

单步超时、尝试总超时、截图预算和清理预算仍分别受限。管理进程撤销令牌后，任何迟到结果均不得提交。不能仅以 `Promise.race()` 返回超时而把仍执行浏览器操作的槽交给下一任务。

### 6.3 退出与遗留进程

服务关闭时停止领取新任务，撤销运行任务权限，有界清理所有执行槽，包括没有关联任务的空闲槽。

持久化执行器归属信息应独立于单个任务，因为浏览器成功完成任务后仍可能存活。至少记录执行器代次、PID、启动时间及其活动任务关联，并按现有存储方式可靠保存。

启动恢复时：

- 先识别和回收上一实例遗留的执行器，再开放对应容量。
- 继续使用 PID 与启动时间校验归属，无法证明归属的进程不强杀。
- 同一执行器即使被多条历史任务引用，也只回收一次。
- 保留任务已消费的尝试次数及绝对恢复期限。
- 正常浏览器轮换不把已成功任务改为中断或失败。

进程组终止范围始终限于该登录槽，不得包含请求浏览器、VNC、主服务或其他登录槽。

## 7. 配置

已通过项目现有统一配置体系接入，支持热更新；环境变量为 `ACCOUNT_LOGIN_BROWSER_REUSE`、`ACCOUNT_LOGIN_BROWSER_IDLE_TIMEOUT_MS`、`ACCOUNT_LOGIN_BROWSER_MAX_ATTEMPTS`、`ACCOUNT_LOGIN_BROWSER_MAX_AGE_MS`。

| 配置含义             | 建议初值         | 语义                                           |
| -------------------- | ---------------- | ---------------------------------------------- |
| 浏览器复用开关       | 首轮上线显式开启 | 关闭时按每次尝试退出执行器，保留旧行为作为对照 |
| 空闲回收时间         | 60 秒            | 从确认清理完成、进入空闲时起算                 |
| 单浏览器最大尝试数   | 20 次            | 达到后完成当前尝试，再退出                     |
| 单浏览器最大存活时间 | 30 分钟          | 达到后不再领取下一任务                         |

期限及次数按现有风格做正整数和上界校验。浏览器最大存活时间不替代尝试总超时。

登录并发继续使用现有配置。调小并发不终止运行中的任务，多余空闲槽应退出；调大并发按任务需求创建新槽。配置变更何时生效应遵守统一配置系统的重启或热更新语义，并在运维文档说明。

## 8. 观察指标与试运行

至少记录以下不含账号秘密的指标或结构化事件：

- 浏览器启动次数、启动耗时、每个浏览器承接的尝试数。
- 执行槽状态、空闲退出次数、周期退出次数、异常重建原因。
- 尝试总耗时、资源清理耗时、批量队列排空耗时。
- 登录成功率、超时率、清理失败数、故障隔离槽数量。
- 登录进程组累计 CPU 时间和内存峰值，以及整机 CPU、内存与交换情况。
- 同期 API 请求响应延迟、排队时间、错误率和请求 Context 可用数量。

CPU 和内存统计应覆盖浏览器子进程，而非只采样 Node Worker；具备条件时使用进程组或 cgroup 口径。跨进程 RSS 相加会重复计入共享内存，应在报告中注明口径，具备条件时补充 PSS。

对照时保持登录并发、请求 Context 容量、机器规格、登录验证步骤尽量一致，同时记录尝试次数、失败重试和同期请求流量。不要仅凭某一时刻 CPU 较低判断有效，也不要用同一批已恢复账号重复登录来制造生产对照。

先观察一次有代表性的集中恢复，并继续观察 3—7 天。初期保持请求 Context 容量不变，确认节省量和稳定性后，再单独评估增加容量。

## 9. 验收条件

### 9.1 功能与资源生命周期

1. 默认并发 1，连续执行 10 个无异常的模拟任务，在未达到轮换上限且不出现空闲间隔时，只启动一个浏览器。
2. 每次尝试创建全新 Context，后一个账号看不到前一个账号的 Cookie 或本地存储；不同账号代理出口正确。
3. 登录 Context 关闭完成后才创建目标验证 Context，所有必要验证仍然通过。
4. 队列空闲达到配置期限后，Worker 与浏览器均退出，不残留临时代理、端口或孤儿进程。
5. 到达次数或时间上限时，只在任务边界轮换，不修改正常任务结果和尝试次数。
6. 并发大于 1 时，各槽独立执行、独立回收；暂停、恢复和缩容符合已有语义。

### 9.2 故障与竞态

1. 覆盖尝试超时、取消、浏览器崩溃、Context 创建卡住及关闭卡住，确认令牌失效且无迟到提交。
2. 成功结果先到而清理失败时，不能复用槽或按普通成功处理；沿用失败监督与回收路径。
3. 旧结果、旧清理消息、旧定时器和执行器异常退出不能清理或完成下一任务。
4. 无法确认进程已退出时隔离槽，不能无限创建新浏览器。
5. 服务在忙碌和空闲状态下重启，均能识别遗留进程；账号删除、凭据更新、Cookie 上传仍能使旧尝试失效。
6. 登录执行器强制回收不影响正式请求浏览器、VNC 或其他槽。

### 9.3 验证方式

扩展现有 `account-login-flow`、`account-login-browser` 和 `target-session-validation` 等相关测试，优先覆盖跨任务隔离、进程回收及消息竞态。模拟测试验证协议；本地浏览器夹具验证实际 Context 生命周期，不以真实 Google 账号反复登录作为自动化测试。

性能验收确认启动次数下降，并比较同等工作量的累计 CPU、资源峰值和请求延迟。若内存持续增长、超时率上升或请求延迟恶化，应关闭复用并保留诊断数据。

## 10. 实施顺序与回滚

建议实施顺序：

1. 分离尝试资源与浏览器资源，先补齐清理确认和异常分支。
2. 增加执行器代次与多任务协议，完成槽状态管理及遗留进程恢复。
3. 接入正常任务间复用、空闲关闭、周期重建和兼容开关。
4. 调整登录与验证 Context 的交接顺序，降低资源重叠。
5. 完成相关测试、指标与运维文档，在生产显式开启观察。

回滚时暂停领取任务，让运行任务完成或按现有规则取消，并确认所有执行器已退出，再关闭复用或部署旧版本。保留账号、任务历史、认证文件、会话版本及人工禁用状态。

实施本方案后，应同步更新 `account-auto-login-operations.md` 等当前运维说明，明确“每次尝试独立浏览器”已变更为“每个登录槽按需复用浏览器”。原始设计文档可保留历史背景，并增加指向本方案的说明。

共享请求浏览器、按实时负载延迟登录、自动扩大请求 Context 池属于后续独立评估项，不纳入本次实现。

## 11. 实施说明

- 执行槽由 `AccountLoginQueue` 管理，Worker 支持顺序执行多个尝试，并通过结果消息和清理确认消息区分完成阶段。
- 已增加执行器独立持久化、消息代次校验、Context 清理检查、空闲回收、任务边界轮换与保守故障回收；尝试总期限不会因复用而延长。
- 自动化测试覆盖连续复用、业务失败、重试、超时、旧消息、空闲退出、缩容、周期重建、遗留执行器及 PID 归属检查；另有本地 Firefox 夹具验证真实 Context 与 Cookie 隔离。
- 队列快照提供浏览器生命周期计数及耗时。进程组 CPU/内存和同期 API 性能需结合服务器监控采样，本次未增加自动扩容或后台负载采样服务。
- 本次未在生产开启复用或增加请求池容量，实际 CPU 收益与内存变化待运营观察。
