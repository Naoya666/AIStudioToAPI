# 前端配置统一管理实施方案

状态：已实施。配置服务、前端草稿表单、账号配置迁移及进程监督重启已接入；实现与验证说明见第 14 节。

## 1. 目标与范围

将用户选定的常用配置统一纳入前端配置管理，同时区分保存后热生效和保存后重启生效。未选中的环境配置继续通过配置文件维护，不自动扩大前端配置范围。

所有配置编辑都先形成草稿，点击“保存”后才提交。开关、选择框和数值输入均不得在编辑时直接改变运行状态。

本次应增加配置管理、持久化、热应用及可靠重启能力，但不借此改变原有请求处理、调度算法或保活机制。特别禁止：

- 将 `MODEL_QUEUE_TIMEOUT_MS` 和 `REQUEST_DISPATCH_TIMEOUT_MS` 拆分成新的独立等待阶段。
- 将 `STREAM_KEEPALIVE_INTERVAL_MS` 扩展为全流程流式保活设置。
- 改动假流式现有的独立保活机制。

## 2. 统一交互规则

| 操作 | 热修改配置         | 重启生效配置           |
| ---- | ------------------ | ---------------------- |
| 编辑 | 仅改变草稿         | 仅改变草稿             |
| 保存 | 校验、持久化并应用 | 校验、持久化，等待重启 |
| 重启 | 继续使用已保存值   | 加载已保存值并应用     |

“保存”实际由后端将配置持久化到服务端；浏览器本地存储至多用于恢复未提交草稿，不能作为服务配置的权威来源。

页面区分以下状态：

1. 当前生效值：系统实际正在使用的配置。
2. 已保存值：持久化的目标配置；重启项有差异时标记为“重启后生效”。
3. 编辑草稿：尚未保存，不因重启而应用。

仅在有差异时展示额外值，避免每项配置重复显示相同内容。未保存草稿不得标记为“重启后生效”。

顶部提供“保存”和“重启”两个按钮，并分别提示：

- 有多少项修改尚未保存。
- 有多少项已保存配置待重启生效；支持展开查看具体变更。

“重启”只加载已保存配置，不隐式保存草稿。存在未保存草稿时，明确提示其不会应用。提供放弃草稿和撤销待重启变更的能力；撤销后重新比较实际运行值和保存值，消除相应提示。

保存混合变更时说明“哪些立即生效、哪些等待重启”。请求、登录任务和已有冷却的生效边界见后文。

## 3. 展示规范

- 主标签显示中文名称。
- 悬停标签或说明图标，显示英文配置名及中文含义；触屏设备允许点击说明图标查看。
- 时间和数量单位直接出现在输入框旁。
- “保存后生效”“重启后生效”、当前运行值和待生效差异直接可见。
- 配置按用途分组，不因支持配置文件参数而全部展示。
- 隐藏配置保留已保存值，不自动清空或恢复默认值。
- API Key 等敏感字段采用遮蔽、显式查看及修改交互，不进入公开看板或日志。

## 4. 前端配置清单与首版生效方式

下表是实施目标，不能将当前所有项误认为已经支持热修改。热修改项需要逐项补充运行时应用逻辑；重启项首版不扩展为动态资源调整。

展示条件说明：

- 通用：所有调度模式展示。
- 旧版：仅 `ACCOUNT_ROTATION_STRATEGY=legacy` 展示。
- 模型调度：`least_recently_used` 和 `least_used` 都展示。

重要约束：

- **不展示 `MODEL_QUEUE_TIMEOUT_MS`**。保留它在文件中的既有默认来源作用；已有逻辑中 `REQUEST_DISPATCH_TIMEOUT_MS` 优先覆盖它。

## 5. 结构化输入

模型配置不要求用户编写 JSON。虽然存储格式是 JSON 对象，前端使用可增加、删除的行输入。

| 配置项                          | 输入列                             |
| ------------------------------- | ---------------------------------- |
| `ACCOUNT_MODEL_MAX_CONCURRENCY` | 模型名、单账号并发上限             |
| `MODEL_MAX_CONCURRENCY`         | 模型名、模型总并发上限             |
| `MODEL_WORKER_ALLOCATION`       | 模型名、最低保障数量、优先分配数量 |

模型名支持从现有模型选择及手动输入真实上游模型 ID；保持现有键名规范，不使用带工具、思考或流式后缀的请求别名。不得仅因下拉列表缺少某个有效上游模型而强制拒绝手动输入。

保存时校验：

- 模型名非空、不重复，数值为符合后端要求的整数。
- 单账号模型并发允许 0；模型总并发必须大于 0。
- 最低保障数量允许 0，优先分配数量必须大于 0，且最低保障不能超过优先分配。
- 优先分配数量总和不超过全局并发；模型并发不得低于其最低保障。
- 删除一行意味着删除该模型单独配置，恢复既有继承或默认规则；不代表禁用模型。

最低保障和优先分配是调度资源概念，不能误标成独立浏览器进程数量。前端负责将行数据转换成后端支持的对象，后端仍执行完整校验。

## 6. 模式与依赖展示

配置表单按草稿中选择的调度模式展示，便于一次配置目标模式。页面另外显示当前运行模式，不能让模式选择框冒充实际运行状态。

例如：当前运行旧版，选择并保存模型调度后，显示“当前运行：旧版；已保存：模型调度，待重启”。目标模式的关联修改一起等待重启，不在旧模式中伪装为已热生效。

其他要求：

- 切换模式不删除另一模式的保存配置。
- 保存显式变更，不将隐藏表单中的旧快照重新写回后端。
- 提前响应头与保活间隔按第 4.6 节建立展示依赖。
- 每日冷却重置关闭时可隐藏或禁用时间输入，并保留时间值。
- 未选择展示的环境配置仍参与校验，例如主端口与公开看板端口冲突、初始化超时之间的关系。

## 7. 已有前端入口

保留原有日志显示条数、登录队列暂停/恢复，以及代理池启用、基础端口、控制端口、程序路径、测试网址、出口 IP 查询网址和检测超时等设置。

统一管理不意味着必须把全部入口搬到设置页：

- 设置页展示第 4.8 节完整配置。
- 账号页保留自动登录及登录并发的便捷入口，但编辑后需要局部“保存”，不直接提交开关。
- 两个入口共用同一权威配置来源和保存逻辑，保存后同步已保存值。
- 不覆盖另一个页面的未保存草稿；有并发修改时提示并要求刷新或处理差异。
- 登录队列暂停/恢复、取消任务、手动登录和账号切换继续作为即时运行操作。
- 代理节点、订阅和绑定继续在专属页面管理。代理池设置遵守编辑后保存；原有必要的 Mihomo 重载行为保留，不误报为全项目重启。

账号模块当前已将自动恢复、登录并发和暂停状态持久化到账号数据库。实施时需要明确迁移或接入关系，保留既有保存值，不能首次上线就被环境变量或默认值覆盖，也不能长期维护两份互相覆盖的权威配置。

## 8. 配置管理与持久化

建立统一配置服务，对每项配置定义类型、中文名称、含义、单位、默认值、适用模式、展示依赖、校验规则及应用方式。

同时维护实际运行配置与已保存目标配置。待重启差异由后端根据两者比较产生，不依赖前端记录“曾经修改过”。当前生效值必须来自实际应用状态，不能直接使用配置文件值冒充。

建议选定配置的加载优先级为：已保存管理配置 > 环境配置 > 默认值。未纳入管理的参数保持原有加载逻辑。恢复环境值/默认值应删除对应管理覆盖值，经过同样校验和应用流程。

持久化文件应位于现有持久化数据目录，不修改源码目录或假设 `.env` 可写。新增配置存储不能依赖自身可变路径造成加载循环。采用原子写入或事务，并带配置版本，避免多个页面覆盖彼此修改。

后端只允许修改清单内及已有获准设置，不接受任意环境变量或文件路径写入。设置接口使用明确目标值，不能继续依赖“反转当前开关”的非幂等行为。

保存流程至少需要：

1. 接收显式变更及基于的配置版本。
2. 校验单项、完整目标配置及本次热应用后的运行配置。
3. 确定即时应用项与等待重启项。
4. 完成持久化和运行时应用，返回真实结果及新版本。

某个热修改依赖尚未生效的重启配置时，该关联修改一起等待重启，并说明原因。例如全局并发扩容需要重启，不能先按扩容后的容量应用关联模型限制。

持久化或热应用失败不得显示整体成功；需要恢复受影响状态或明确报告实际保存/应用结果。避免不可回滚副作用发生后仍宣称已恢复。

## 9. 热生效边界

- 请求参数在后续请求生效，已执行请求尽量保留其接受时的参数快照。
- 排队超时修改不延长或缩短已排队请求的既定期限。
- 降低队列容量不驱逐已排队请求，后续入队遵守新限制。
- 降低并发上限不强行终止运行请求，后续派发遵守新限制。
- 冷却参数影响之后新产生的冷却，不自动重算已有冷却。
- 登录参数影响后续任务或尝试，不重置已有任务期限，也不终止正在执行的登录尝试。
- 日志保留策略在后续清理时应用；已删除数据无法恢复。
- 定时功能修改必须更新实际定时任务，不能仅更新配置对象。
- 浏览器日志等跨组件设置须执行原有同步逻辑。

实现时核查配置是否被构造函数复制、被定时器捕获或传入工作进程；修改一个共享对象不等于已经实现热修改。

## 10. 重启流程

当前 `main.js` 具备启动与信号退出流程，但不提供可靠的自重启能力；Docker 当前直接执行 `node main.js`。不能将 `process.exit()` 本身视为重启功能。

实施时选择适合项目运行方式的进程监督方案，例如稳定父进程管理服务子进程，或接入明确存在的外部进程管理器。需覆盖实际支持的源码和容器启动方式，不假定退出后必然被拉起，也不要求开放宿主机 Docker 控制权限。

重启应：

1. 校验已保存配置，拒绝并发重复重启。
2. 告知前端已接受重启操作，停止接收新业务请求。
3. 给执行中请求有限的收尾时间，关闭浏览器、数据库和相关进程资源。
4. 重新启动服务并加载保存配置。
5. 前端等待健康状态恢复，再读取运行配置及启动实例标识。
6. 只有确认新实例正常运行且配置实际生效后，才清除待重启提示。

启动失败时保留错误信息和上一份可用配置，提供恢复途径，避免无限重启循环。不能因健康接口短暂可访问就判定全部配置已经生效。

## 11. 实施顺序建议

1. 梳理配置元信息和已有存储，完成运行值、保存值、草稿及版本管理。
2. 实现后端校验、持久化和清单内热修改逻辑。
3. 实现中文表单、模式展示、依赖展示和结构化模型输入。
4. 将账号页及原有设置接入统一保存规则，保留入口及旧保存值。
5. 实现可靠重启、状态恢复及失败恢复。
6. 完成有针对性的验证和项目要求的检查。

## 12. 验收要求

- 前端展示范围严格符合本文清单；不新增未选中的环境设置。
- 修改任何设置都不在点击保存前改变系统行为。
- 保存后的热修改重启后仍保留；重启项在重启前显示真实运行值和保存值。
- 页面刷新、换设备后仍能看到待重启差异。
- 重启不隐式提交草稿，失败不伪装成配置已经生效。
- 调度模式切换、隐藏字段保留及关联等待重启符合本文规定。
- `REQUEST_DISPATCH_TIMEOUT_MS` 延续现有覆盖逻辑，`MODEL_QUEUE_TIMEOUT_MS` 不在前端展示。
- 提前响应头控制等待保活字段展示，实际保活范围及假流式行为不改变。
- 模型键值行能新增、删除、校验并正确往返转换，不要求编辑 JSON。
- 账号页与设置页保存同一配置，原有账号配置在升级后不丢失。
- 并发保存冲突、写入失败、热应用失败及重启失败有可辨认的实际状态。
- 新配置存储纳入持久化目录；原有启动方式、API 请求及账号任务正常运行。

## 14. 实现与运维说明

### 14.1 服务端权威配置

- `src/config/definitions.js` 定义本文选定配置及原有日志显示、调试日志设置的元信息；未纳入的环境参数仍由原加载器读取。
- `src/config/ConfigurationService.js` 维护运行值、保存值和配置版本，执行完整目标与热应用后运行配置的校验。管理覆盖文件固定为工作目录中的 `data/managed-config.json`，采用原子替换、私有权限及单调递增版本，不修改 `.env`。
- 控制台通过需要认证的 `/api/configuration` 读取和保存配置。保存只提交显式变更及基础版本；过期版本返回 409。`reset` 删除对应管理覆盖值，恢复环境值或默认值；同样需要保存并经过校验。
- API Key 在普通配置响应中遮蔽；显式查看通过认证后的 `/api/configuration/secrets` 获取。密钥修改同时影响后续 API 认证及未配置独立密码时的控制台登录，已有已登录会话继续有效。原有设置接口改为明确目标值和版本检查，不再反转开关。
- 模式变更关联配置等待重启；尚未生效的并发资源变更会推迟相关并发限制。无资源依赖的超时、冷却等设置仍可热应用。

### 14.2 账号及代理池设置

首次初始化从账号数据库迁移自动登录和登录并发的已保存值；迁移标识写入管理配置。此后管理配置成为唯一来源，账号数据库仅保存队列暂停状态，避免旧副本覆盖新配置。账号页保存与设置页共享同一版本，轮询同步保存值但保留未提交草稿。

代理池仍使用既有专属存储与应用流程。启用开关、端口、程序路径及检测参数先形成草稿，再通过局部保存提交显式变更；设置修订检查防止并发覆盖。保存会执行必要的 Mihomo 重载，无需全项目重启；应用或持久化失败会尝试恢复此前的 Mihomo 状态，并明确报告恢复失败。

### 14.3 重启与恢复

`node main.js`、`npm start`、`npm run dev:server` 及现有 Docker CMD 都通过同一稳定父进程监督服务子进程，无需 Docker 控制权限。重启接口先返回接受结果并拒绝重复重启，随后停止新业务请求，为执行中请求提供最多 15 秒收尾时间，再关闭原有资源。关闭阶段设有有限期限，监督器会清理超时的服务进程组。

前端保留草稿，等待新启动实例的标识、配置版本、实际运行配置及运行健康状态；没有可用认证账号时，账号绑定模式视为可用，预热目标为 0 时保留既有按需初始化行为。其他情况下，需要初始化上下文达到健康状态，不能仅凭 HTTP 监听成功宣称重启完成。

父进程保存 `data/managed-config.last-good.json`，并将启动失败信息保存在 `data/restart-status.json`。新配置启动失败时只尝试一次上一份可用配置；已保存目标不被覆盖，恢复实例仍显示待重启差异和失败原因。可在控制台修改配置或撤销待重启变更后再次重启。恢复实例也无法启动时，服务退出，不无限循环；停止服务后可备份现有管理配置，再用 `managed-config.last-good.json` 恢复 `managed-config.json`，并检查未纳入管理的环境配置及系统资源。

控制台会话保存在私有的 `data/console-sessions` 目录，监督重启使用相同会话签名密钥，避免重启等待期间丢失登录状态。正常重启不会提交浏览器草稿。

### 14.4 生效边界与验证

请求处理器和转换器按接受时的配置快照读取请求参数；调度限额影响后续派发，排队期限和已有冷却不重新计算。登录服务更新后续任务和尝试的配置，不重置已有期限或暂停状态。每日冷却重置会重新安排实际定时器；调试日志保留原有浏览器同步调用。两种调度等待超时的合并读取、提前流式等待保活及假流式随机保活保持原有语义。

新增测试：

- `tests/unified-configuration.test.js`：清单范围、持久化、版本冲突、模式与资源依赖、完整校验、账号迁移、写入与热应用失败、定时任务、请求快照和失败恢复状态。
- `tests/configuration-restart.test.js`：使用真实父子进程和 HTTP 接口验证重启、重复拒绝、会话保留、单次失败恢复及再次重启。
