# 调度面板今日用量与预估额度设计

## 1. 背景与目标

当前“模型调度”面板中的调用次数来自 `ModelScheduler` 的持久化累计计数。该数字会跨天、跨进程重启累加，而“使用统计”分页已经负责完整历史统计，因此调度面板继续展示累计调用次数价值有限。

本次改造的目标是：

1. 将调度面板的模型汇总和“账号 × 模型详情”中的请求数改成当前太平洋自然日内的请求数。
2. 新增“预估剩余额度”汇总板块，按 Flash 每账号每模型 100 次、Pro 每账号每模型 10 次估算，只展示全局总数。
3. 将 HTTP 403 视为可恢复的短时风控，而不是永久的模型不支持状态。
4. 在现有“一键重置所有账号 429 状态”旁新增“一键启用所有账号”，用于人工解除所有调度层面的禁用与冷却状态。

本设计不改变 API 协议转换、认证文件格式、浏览器 Context 架构、请求重试预算或使用统计分页。

## 2. 现状与影响范围

相关实现主要位于：

- `src/core/ModelScheduler.js`：账号 × 模型状态、累计尝试次数、错误分类、批量恢复和 `/api/status` 所需快照。
- `src/core/ScheduledRequestHandler.js`：在真实发送上游请求前调用 `startAttempt()`，并按错误分类决定是否换账号重试。
- `src/routes/StatusRoutes.js`：调度状态和恢复接口。
- `ui/app/components/SchedulerStatus.vue`：调度面板、模型汇总、账号 × 模型详情和恢复按钮。
- `ui/locales/zh.json`、`ui/locales/en.json`：中英文文案。
- `data/scheduler-state.json`：调度状态持久化文件。

仅修改前端无法准确满足需求：今日请求数必须在每次上游尝试发生时记录，403 的状态语义和批量恢复也属于后端调度逻辑。因此实现阶段需要同步调整后端快照/API和前端展示。

## 3. 统计口径

### 3.1 “今日”的定义

“今日”固定按 IANA 时区 `America/Los_Angeles` 计算，统计区间为：

> 最近一个太平洋时间 00:00（含）至当前时刻

不使用固定的 UTC-8 偏移。这样会自动处理太平洋标准时间 PST（UTC-8）和夏令时 PDT（UTC-7），包括每年 23 小时或 25 小时的切换日。

后端为当前时间生成太平洋日期键，例如 `2026-09-10`。只要日期键变化，就在下一次计数或读取快照时惰性切换到新的一天。无需依赖必须准时触发的午夜定时器。

### 3.2 “请求数”的定义

今日请求数统计真实发送到 Google 上游的尝试次数，而不是进入本站的逻辑 HTTP 请求数：

- 在 `startAttempt()` 首次执行时计数。
- 同一个用户请求因 403、429 或 5xx 切换账号重试时，每次真实上游尝试分别计数。
- 排队后未取得租约、取得租约但尚未发送就取消、本地 Context 不可用且未发送的情况不计数。
- 请求跨越太平洋午夜时，按实际调用 `startAttempt()` 的日期归属。
- 成功和失败的上游尝试都计数，因为它们都可能消耗或反映 Google 配额。

该口径与当前调度器累计字段 `request_count` 的语义一致，也比使用统计分页中的逻辑请求总数更适合估算额度。

### 3.3 成功与失败列

本次只将“调用次数”改为“今日请求数（PT）”。现有“成功”和“失败”列继续展示累计值，不改变其语义和持久化数据，以避免把本需求扩大成整套按日分析报表。列名和提示中要明确区分“今日请求数”与累计成功/失败。

## 4. 数据模型

在每个账号 × 模型 slot 中保留现有累计计数，并新增：

```js
{
    request_count: 8984,            // 现有累计值，继续供 least_used 和历史兼容使用
    daily_request_count: 37,        // 当前太平洋日期内的上游尝试数
    daily_request_date: "2026-09-10" // America/Los_Angeles 日期键
}
```

新增内部方法建议为：

```js
getPacificDateKey((now = Date.now()));
rolloverDailyUsage(slot, (now = Date.now()));
```

行为如下：

1. `slot()` 创建新状态时，将日期键设为当前太平洋日期、计数设为 0。
2. `startAttempt()` 先执行日切，再同时递增累计值和今日值。
3. `snapshot()` 读取 slot 前执行日切，确保即使午夜后暂时没有请求，页面也立即显示 0，而不是昨天的数据。
4. 日切只清零 `daily_request_count`，不改变累计请求数、成功/失败、限流、冷却或健康状态。
5. 新字段随调度状态一并原子持久化，服务重启后继续当天计数。

### 4.1 持久化兼容

建议将调度状态版本升级为 2，并让加载器同时接受版本 1 和版本 2：

- 版本 2：直接读取新增日统计字段，并校验非负整数和合法日期键。
- 版本 1：保留全部旧状态；由于旧累计值没有时间戳，无法可靠拆出“今日”部分，新增日统计从 0 开始。
- 首次升级当天的今日请求数和预估剩余额度可能少计/高估；到下一个太平洋 00:00 后自然恢复为完整日口径。
- 不使用 `usage-stats.jsonl` 自动回填调度计数。其记录以完整 HTTP 请求为单位，重试 attempt 没有独立时间戳，强行回填可能造成跨午夜归属错误或与启动后的实时增量重复。

实施时在升级日志中打印一次上述兼容提示。现有历史累计数据不会丢失。

## 5. 403 风控处理

### 5.1 错误分类调整

当前明确包含 `PERMISSION_DENIED` 的 403 会被归为 `unsupported`，导致该账号 × 模型在手动恢复前永久不可调度。按新的业务判断，调整为：

1. `status === 403` 优先归类为新的 `risk_controlled`（或复用 `temporary`，推荐使用独立分类以便测试和后续展示）。
2. `risk_controlled` 只影响当前账号 × 模型，不设置 `account.healthy = false`，也不设置 `slot.unsupported = true`。
3. 使用现有临时错误退避基数 `TEMP_ERROR_COOLDOWN`：连续失败按 30、60、120、最多 120 秒冷却（默认配置下）。
4. 在尚未输出模型内容且重试预算允许时，继续换另一个账号重试。
5. 没有 HTTP 403 状态码、但有明确且可信的“模型不支持/账号无模型权限”语义时，仍可归为 `unsupported`；这样不会取消对真正模型权限差异的支持。

状态优先级必须先判断 403，再判断消息中的 `PERMISSION_DENIED`，否则新规则不会生效。

### 5.2 为什么不把 403 直接当作 429

403 与 429 都是账号 × 模型粒度且可恢复，但保留不同分类有两个好处：

- 现有“一键重置 429”仍保持严格语义，不会暗中扩大作用范围。
- 后续可以独立调整 403 风控冷却时间或在监控中展示，而无需迁移状态。

首版无需新增单独的 403 表格列；403 会呈现为 `COOLDOWN`，最近错误中保留上游消息。

## 6. “一键启用所有账号”

### 6.1 操作语义

新增调度器方法 `resetAllAccounts()`。它先遍历 `authSource.getRotationIndices()` 实例化当前有效轮换账号，再对这些账号执行：

- 账号级：`healthy = true`、`last_error = null`。
- 所有模型 slot：清除 `unsupported`、`rate_limited`、`cooldown_until`、`consecutive_failures` 和 `last_error`。
- 保留累计和今日请求数、成功/失败数、最近使用时间、当前 inflight 和活动租约。
- 完成后立即持久化并调用 `drain()`，让排队请求重新参与调度。

该操作是人工覆盖当前调度判断，不承诺账号真实可用。按钮点击后到达的新 403、429、认证失败仍会重新设置相应状态。

### 6.2 安全边界

“启用所有账号”只恢复调度器内存/持久化状态，不执行以下操作：

- 不修改 auth JSON 中的 `expired` 标记。
- 不重新加入被去重淘汰、文件已删除、JSON 无效或不在 `getRotationIndices()` 中的账号。
- 不伪造登录成功，不自动刷新 Cookie。
- 不关闭或重建浏览器 Context。

因此按钮不会将物理上无效的认证文件错误地显示为可调度账号。若要恢复 expired auth，仍使用现有账号管理流程。

批量恢复采用与现有 429 批量恢复相同的并发策略：允许存在活动请求，原子地同步清理状态但不动租约；随后到达的错误可以再次设置状态。

### 6.3 API

新增认证接口：

```http
POST /api/scheduler/reset-all
Content-Type: application/json

{}
```

成功响应：

```json
{
  "success": true,
  "reset_account_count": 12,
  "reset_model_count": 24
}
```

两个计数只统计本次实际发生状态变化的账号和 slot，便于前端给出可信反馈。legacy 模式沿用现有行为返回 409。

保留现有 `POST /api/scheduler/reset-rate-limits`，不改变兼容性。

## 7. 预估剩余额度

### 7.1 配额规则

首版按实际上游模型 ID 的独立 slot 估算：

- 模型名包含独立词段 `flash`：每日 100 次/账号/模型。
- 模型名包含独立词段 `pro`：每日 10 次/账号/模型。
- `flash-lite` 仍属于 Flash，按 100 次计算。
- 不匹配 Flash/Pro 的模型（例如 embedding、imagen、`__files__`）不纳入估算。
- `-high`、`-search` 等请求侧变体已在申请调度租约前转换为真实上游模型，因此不会被重复视为独立额度。

匹配应基于以 `-` 分隔的模型词段，而不是简单的任意子串，避免误判。配额规则集中放在一个后端常量/辅助函数中，前端不重复实现。

### 7.2 纳入统计的账号和模型

- 账号集合使用 `authSource.getRotationIndices()`：只统计当前有效、未 expired、按邮箱去重后的真实轮换账号。
- 不因临时 `UNHEALTHY`、`RATE_LIMITED`、`COOLDOWN` 或 `UNSUPPORTED` 状态扣除账号的理论日额度；这些是可恢复调度状态，“剩余额度”仍按已尝试次数估算。明确标记为 `playground_verification` 的账号不贡献 Playground 次数和 Token 预算，历史用量仍保留，Build 预算独立计算；详见[验证403与批量恢复](verification-403-and-batch-recovery.md)。
- 模型集合与调度面板一致：配置在 `MODEL_WORKER_ALLOCATION` 中、正在排队或已经产生过 slot 的模型并集。
- 尚未配置、从未请求且调度器完全未知的模型不纳入总数，避免仅因 `configs/models.json` 中存在大量可展示模型就虚增额度。

### 7.3 计算公式

对每一个“有效轮换账号 × 已知且支持配额估算的模型”：

```text
slot 剩余 = max(0, 该模型日上限 - slot 今日请求数)
总预估剩余额度 = 所有 slot 剩余之和
```

示例：12 个有效账号，已知模型为两个 Flash；今日两个模型分别总共尝试 34 和 33 次：

```text
总初始额度 = 12 × 2 × 100 = 2400
总预估剩余额度 = (1200 - 34) + (1200 - 33) = 2333
```

单个 slot 即使超过日上限也只贡献 0，不产生负数。由于 Google 可能不对所有失败请求计费、账号可能存在差异化额度或外部消耗，该值必须明确标注为“预估”，不能称为 Google 返回的真实余额。

### 7.4 快照字段

`GET /api/scheduler` 以及 `/api/status` 中嵌入的 scheduler 快照新增：

```json
{
  "usage_window": {
    "date": "2026-09-10",
    "timezone": "America/Los_Angeles"
  },
  "estimated_remaining_quota": 2333,
  "quota_tracked_accounts": 12,
  "quota_tracked_models": 2,
  "models": [
    {
      "model": "gemini-3.7-flash",
      "daily_requests": 34
    }
  ],
  "accounts": [
    {
      "models": {
        "gemini-3.7-flash": {
          "daily_requests": 4
        }
      }
    }
  ]
}
```

前端只消费 `estimated_remaining_quota` 和两个层级的 `daily_requests`，不自行计算配额。`quota_tracked_accounts/models` 用于提示或诊断，不展示单账号余额。

## 8. 前端设计

调度卡片建议调整为以下顺序：

```text
模型调度
逻辑执行槽：…
浏览器 Context：…

┌────────────────────────────────────────────┐
│ 预估剩余额度                         2,333 次 │
│ 太平洋时间今日 · Flash 100 / Pro 10         │
└────────────────────────────────────────────┘

[一键重置所有账号 429 状态] [一键启用所有账号]

模型 | 今日请求数（PT） | 成功 | 失败 | …
...
▸ 账号 × 模型详情
    模型 | 状态 | 在途请求 | 今日请求数（PT） | 失败 | …
```

交互要求：

- 两个批量按钮共用现有 busy 状态，操作期间均禁用，避免重复提交。
- “一键启用所有账号”属于广泛状态覆盖，点击后先使用浏览器确认框说明作用范围；确认后再请求接口。
- 成功提示包含恢复账号/模型数量；无变化时提示“所有账号已处于启用状态”。
- 失败沿用当前错误区域，并处理后端 401、409 和 500。
- 额度板块只显示一个总剩余数字，不增加单账号余额列，也不在账号详情中展示余额。
- 在“预估剩余额度”标题或说明上提供 tooltip，说明估算公式、太平洋日界线和外部用量不可见的限制。
- 中英文文案同步更新；原 `schedulerRequests` 不复用，新增含义明确的 `schedulerTodayRequests`。
- 小屏下额度板块与按钮允许换行，现有表格继续横向滚动。

## 9. 后端实现拆分

建议按以下顺序实施：

1. 在 `ModelScheduler` 增加太平洋日期键、slot 日计数和惰性日切。
2. 在 `startAttempt()` 同步维护累计/今日计数，在 `snapshot()` 输出今日汇总和总预估余额。
3. 调整 403 错误分类及冷却行为。
4. 实现 `resetAllAccounts()` 和 `/api/scheduler/reset-all`。
5. 更新 `SchedulerStatus.vue`，新增额度板块、按钮、确认交互和今日请求列。
6. 增加中英文文案并更新调度说明文档。

## 10. 测试方案

### 10.1 单元测试

在 `tests/model-scheduler.test.js` 覆盖：

- 同一太平洋自然日多次 `startAttempt()` 正确累计，重复调用同一 lease 仍只计一次。
- PST、PDT 日期和夏令时切换前后生成正确日期键。
- 跨太平洋午夜后 slot 惰性清零，累计 `request_count` 不清零。
- 重启加载版本 2 状态后保留当天计数；加载版本 1 时安全初始化为 0。
- 模型总今日数等于账号 slot 今日数之和。
- Flash、Flash Lite、Pro 的额度匹配正确，embedding/imagen/内部模型被排除。
- 余额按 0 截断，不出现负值。
- expired 和重复账号不计入额度基数；临时不可用状态仍计入理论额度。
- 403（包括带 `PERMISSION_DENIED` 的 403）进入短冷却而非 `UNSUPPORTED`，且可按现有预算换账号重试。
- 无状态码但明确模型不支持的错误仍进入 `UNSUPPORTED`。
- `resetAllAccounts()` 清除所有可恢复状态，但保留统计、inflight 和活动租约。

### 10.2 路由与请求测试

在调度请求/路由测试中覆盖：

- 一次逻辑请求发生两次上游尝试时，今日数增加 2。
- 未真实发送的失败不增加今日数。
- `/api/scheduler/reset-all` 未认证、legacy 模式、成功和无变化响应。
- 活动请求存在时批量启用不破坏租约，之后的新错误仍能重新进入冷却。

### 10.3 前端与构建检查

- 模型汇总和账号详情均读取 `daily_requests`，不再展示累计 `request_count`。
- 页面只出现一个总额度数字，不出现账号余额。
- 确认、成功、无变化和失败提示正确。
- 执行 `npm test`、`npm run lint`、`npm run build:ui`。

## 11. 验收标准

1. 页面“今日请求数（PT）”在同一天内随每次真实上游尝试增长，并在太平洋 00:00 后归零。
2. 模型汇总值等于账号详情对应 slot 的今日请求数之和。
3. 服务在当天重启后计数不丢失。
4. 403 不再把模型永久标记为 `UNSUPPORTED`，冷却结束或人工启用后可再次调度。
5. “一键启用所有账号”能恢复账号级和模型级调度状态，但不会恢复 expired/缺失/重复认证文件。
6. “预估剩余额度”严格使用有效轮换账号、已知 Flash/Pro 模型和今日尝试数计算，最低为 0。
7. 前端不展示任何单账号预估余额。
8. 原 429 专用按钮、单账号/单模型恢复、累计调度统计和使用统计分页保持可用。

## 12. 已知限制

- 预估值不知道同一 Google 账号在本服务之外的调用量。
- 假设 Flash 100、Pro 10 对所有纳入账号一致；Google 若动态调整或对账号差异化限制，页面不会自动感知。
- 失败尝试按一次额度消耗估算，可能比 Google 实际扣减更保守。
- 首次从旧版状态升级的当天无法从无时间戳累计值中精确还原今日数；下一太平洋自然日起准确。
- 多个服务进程若分别使用同一批 Google 账号但不共享调度状态，各自只能看到本进程用量，总剩余会被高估。现有调度器本身也不支持跨进程共享租约。
