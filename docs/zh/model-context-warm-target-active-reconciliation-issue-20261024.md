# 问题日志：模型预热目标未主动约束初始化，混合流量下覆盖持续不足

日期：2026-10-24（UTC）。最新需求澄清：2026-10-25（Asia/Shanghai）。状态：已完成项目本地实现和离线验证，生产部署及持续混合流量验收待进行。现场配置与复现保留原诊断时点事实，改造以第 5 节最新规则为准。

诊断基线：`ef6ad68a8deecb316f1f98387d94cce994047e8e`，已部署于 meow_us / meow_jp。本日志独立记录用户澄清后的需求、现场证据、实现缺口及后续验收要求；不表示问题已修复。

## 1. 用户澄清的初衷

设置模型预热目标的一项主要目的，是解决模型流量不平衡时的无效初始化和排队。目标应当主动介入账号选择、初始化机会分配、Context 驻留及置换，使池子持续向所配置的模型覆盖目标收敛。

用户举例：3.5 Flash 的可用额度充足，而仍有 3.8 Flash 额度的账号几乎都同时具有 3.5 Flash 额度。在这个条件下，可以排空多余的、已经无法服务 3.8 Flash 的 Context，换入仍能服务 3.8 Flash 的账号；新 Context 同时可以继续处理 3.5 Flash。

这是说明覆盖重叠关系的例子，不能将“3.8 账号一定支持 3.5”写成通用规则，也不能把算法硬编码为这两个模型。实际选择依据当前账号对目标模型的准入和可用状态；不要求先证明其他模型不受影响。用户已明确：管理员负责模型比例取舍，目标允许牺牲其他模型的体验，不引入其他模型充分覆盖或额度无损的替换前提。

**核心要求：模型预热目标应是主动纠正池子分布的调度目标，不能只在初始化资源无人竞争、池子未满时参与一次后台排序。**

目标仍有真实可满足性边界：可用账号不足、权限限制、模型冷却、多个目标无法兼容等情况可以产生缺口。但“其他模型还有请求”或“历史按需 Context 已经填满池子”，不能在存在可用目标候选和安全排空机会时，成为长期不修复覆盖的理由。安全仅指不打断在途请求、容量及生命周期正确，不包含其他模型体验无损。

## 2. 现场配置与现象

| 节点 | 最大 Context 数 | 3.8 Flash 覆盖目标 | 后台容量上限 | 策略 |
| --- | ---: | ---: | ---: | --- |
| meow_us | 12 | 10 | 11 | different_proxy_first |
| meow_jp | 5 | 4 | 4 | least_recently_used |

配置项为 `MODEL_CONTEXT_WARM_TARGETS`，模型 ID 为 `gemini-3.8-flash`。

美国在临时暂停入口、清除排队后，曾成功预热到 `ready=10 / target=10 / deficit=0`。恢复混合流量后，覆盖很快下降，重新出现明显排队。这说明冷启动达标不能代表持续运行中的分布维护有效。

诊断时的一次美国快照：

- 总占用 12 个 Context，其中 11 个 BUSY、1 个 CLOSING；41 个活跃 worker，33 个排队请求。
- 3.8 Flash：78 个按本地策略符合资格的账号，就绪覆盖 2，目标 10，缺口 8；31 个排队请求。
- 3.5 Flash：205 个按本地策略符合资格的账号，就绪覆盖 11；8 个活跃 worker，无排队。
- 3.1 Pro：34 个按本地策略符合资格的账号，就绪覆盖 1；2 个排队请求。

这些是单次动态采样，不是吞吐对照实验。“按本地策略符合资格”也不代表已逐个验证 Google 真实剩余额度。但该快照说明：配置已生效，池子对目标模型的覆盖仍严重不足，而其他模型具有大量重叠可用覆盖。

## 3. 已确认的实现缺口

### 3.1 初始化入口没有统一服从覆盖协调

`BrowserManager._poolCandidates()` 的合并顺序是：

```js
[...demanded, ...coverageWarm, ...warm]
```

- `demanded` 优先处理真实排队请求选出的账号，只要求它能处理对应请求模型。
- `coverageWarm` 才按模型预热缺口计算收益。
- 普通 `warm` 主要检查共享池驻留资格，不要求候选能补足当前目标模型。

因此，3.8 已不可用、3.5 仍可用的账号，仍可从其他模型的按需路径或普通补池路径进入初始化。不能把每个“3.8 不可用账号被初始化”的现象都认定为 `coverageWarm` 直接选错了账号；应记录实际入口和请求模型逐条归因。

`ModelScheduler._signalContextDemand()` 为某个排队模型选冷账号时，目前主要考虑该请求模型的资格、账号顺序和出口分散，没有把全池预热缺口纳入等价候选的选择。

在候选 A、B 都能处理 3.5 请求，而只有 B 能同时补足 3.8 缺口时，当前路径仍可能选择 A。全局初始化并发又由这些路径共同竞争，覆盖补池可能持续得不到机会。

### 3.2 “仍可服务其他模型”使低价值分布长期存续

`isAccountPoolResident()` 和 `_canKeepPooledContext()` 使用共享池驻留资格。账号只要仍能服务某些模型，就可能被保留；一个模型的目标缺口本身，不会使冗余的其他模型 Context 退出。

满池时的实际请求置换虽然会用 `_warmEvictionLoss()` 排序，但它只是已有可置换候选的偏好，不能独立完成主动排空和覆盖恢复。

在持续流量下，仅等待冗余 Context 自然空闲也可能长期无法纠正分布。需要有主动的安全排空机制：停止给选中的冗余 Context 追加租约，等待在途请求完成，再释放并换入更有覆盖价值的账号。具体排空算法尚待设计；现有请求不能因此被强制中断。

### 3.3 真实需求填到最大容量后，后台覆盖修复被挡住

当前覆盖候选只在以下条件下被允许：

- 实际占用小于 `background_capacity`，可以新增；
- 实际占用等于 `background_capacity`，且存在能改善覆盖的空闲置换。

美国后台上限为 11，但真实需求可以将占用推到 12。此时上述两个条件均不成立，覆盖候选直接被过滤。即使存在空闲、可安全替换且替换后能改善目标的 Context，也可能没有覆盖修复候选。

`_reserveContextCapacity()` 的后台覆盖置换入口也依赖“等于后台上限”的判断，需要与候选规划一起修正，不能只修排序。

上述 M-1 是诊断基线的已实现行为，不是最新需求。用户进一步确认：自由槽是可正常驻留、调用和置换的共享名额，不是物理空位。因此后续应取消后台 M-1 物理占用上限，允许普通补池将池子填到 M；满池仍须支持主动排空与覆盖修复。

### 3.4 本地资格和“真实额度用尽”并非同一状态

`isResourceEligible()` 主要检查健康、禁用、认证、层级/白名单、unsupported 和有效冷却，不以面板预估剩余额度为零作为排除依据。冷却到期后，账号可以再次被视为符合资格。

后续诊断必须区分：

1. 明确处于目标模型不可用/冷却中的账号，由其他模型路径选入；
2. 冷却已过、按当前本地状态重新符合资格，但真实上游额度仍不足的账号。

本次需求重点是初始化和池分布协调。429 分类、冷却与真实日额度识别是另一项工作，不能以修改这些策略代替本问题的修复。

## 4. 已做的离线最小复现

通过当前生产类的真实方法配合内存中的模拟账号状态，复现了两个行为，没有修改生产数据：

1. 目标模型存在缺口时，其他模型的 `demanded` 账号即使对目标模型不可用，仍排在覆盖候选前面。
2. 最大容量 4、后台上限 3、实际占用 4，全部 Context 均空闲；目标覆盖为 1/3，存在冷账号，替换一个空闲 Context 可增加一份覆盖，但 `_poolCandidates()` 返回空数组。

第二个场景排除了“没有可用账号”及“没有空闲 Context”两种原因，直接暴露了满池覆盖修复的容量判断缺口。

既有测试覆盖了后台上限处的置换、按需使用额外槽位等场景，但不足以证明实际需求填满后，覆盖仍能恢复；也不足以证明持续混合流量下初始化机会不会偏离目标。

## 5. 后续修改需要达到的行为

以下规则按 2026-10-25 的用户澄清更新，尚未实现。采用简单、可解释的调度，不扩展为全模型无损或全局最优分配系统。

1. **目标主动优先。** 模型覆盖有缺口且存在可用候选时，优先安排目标初始化，不等到其他来源都没有任务才补目标；必要时可以牺牲其他模型体验。
2. **请求选号兼顾目标。** 对同样能处理请求的冷账号，优先选能补足模型目标的账号，再考虑出口分散和原有账号顺序。
3. **自由槽正常使用。** 自由槽是不受预热覆盖保护的共享名额，可预热、驻留、接请求和动态换账号；普通补池可以跑满 M，不再强制后台最多 M-1。
4. **可用账号不足释放共享名额。** 例如 M=12、目标 10、实际仅 6 个目标可用账号，尽量覆盖这 6 个，其余 6 个名额都按共享逻辑使用；至少一个名额保持自由调度。自由槽不绑定固定账号，也可能支持目标模型。
5. **优先排空自由槽。** 请求按需初始化和模型目标补池需要腾位置时，都优先选自由槽；空闲则关闭，繁忙则停止追加租约、等待已有请求完成，再关闭并初始化新账号。不是永久等待自然空闲，不强杀在途请求。
6. **不要求替换无损。** 其他模型仍有额度或仍有请求，不构成目标补池主动替换的否决条件；不增加冗余覆盖证明、全模型额度包含关系推断或多步最优置换算法。自由槽优先不应成为禁止原有真实请求置换其他账号的硬约束。
7. **统一选号，复用执行。** 启动/普通补池、请求按需、模型补池和恢复后的普通池选号使用一致的目标优先规则；继续复用 `_startPooledContext`、`_getOrStartContextInit`、同账号去重、容量预留和初始化并发控制。不要独立新增一条主动预热创建通道。
8. **原有机制继续工作。** 专用故障恢复、管理重建保持必要流程；权益检测临时 Context 与登录浏览器不作为模型补池候选。真实请求依然可以连续触发空闲 Context 的关闭和创建，不新增驻留保护期、销毁延迟、节流和次数限制。
9. **持续重新协调。** 资格/冷却变化、租约释放、初始化完成/失败和关闭完成后继续评估，满池时也可推进。共享名额不等于超限容量，驻留、初始化、关闭和容量预留仍严格计数。
10. **保留配置防呆。** 单模型目标继续要求 `0 <= T < M`，前后端均校验；运行时至少留一个共享名额，不将所有位置变成不可自由置换的覆盖保护名额。多个目标可重叠，不新增复杂的重叠求解。

普通池的初始化来源包括启动/全局补池、请求按需、模型补池、故障恢复及管理重建。目前已有资源准入控制，缺口在于账号选择和初始化机会分配：`demanded → coverageWarm → warm` 的固定拼接允许其他入口长期绕过目标。改造集中于这些选择规则及自由槽优先排空，已有底层创建队列继续使用。

目标已满足或无合格目标候选时，按原有共享逻辑处理其他模型需求；目标不构成其他模型调用禁令。管理员自行决定健康比例，不要求程序保护所有模型的体验。

## 6. 必须补充的验收场景

| 场景 | 期望行为 |
| --- | --- |
| 3.8 目标不足；3.5 请求可由两类账号执行，一类同时支持 3.8 | 优先初始化兼顾两者的账号，不选仅支持 3.5 的等价候选 |
| 目标有缺口，池内账号仅服务其他模型，冷账号可服务目标模型 | 主动排空并换入目标账号，不以其他模型覆盖或体验下降为否决条件 |
| 其他模型反复产生冷初始化需求，3.8 持续排队且有资格账号 | 3.8 覆盖修复获得初始化机会，不被固定入口优先级长期饿死 |
| 池子已达到 M，目标覆盖不足 | 优先排空自由槽并恢复覆盖，不因池满过滤全部覆盖候选 |
| 冗余 Context 持续繁忙但每个请求都可正常结束 | 可停止追加租约并排空，等待完成后置换；不无限等待自然空闲，不强杀在途请求 |
| 只剩目标模型不可用、其他模型仍可用的账号 | 自然降级并共享容量，不为了形式上的目标反复初始化已知无贡献的账号 |
| 自由槽支持目标模型，或多个模型覆盖重叠 | 自由身份不由是否支持目标模型单独决定，不要求全模型无损替换 |
| 候选已在初始化、排空、关闭或容量预留中 | 不重复安排，计数不超限；取消、失败和晚到完成正确清理 |
| 覆盖候选位于少数出口，其他出口只有目标模型不可用账号 | 模型覆盖优先，不能为了出口均衡制造无效初始化 |
| 全局保温目标为 M、账号足够 | 共享槽正常预热，允许占满 M，不人为保留物理空位 |
| M=12、目标 10、目标可用账号仅 6 个 | 剩余 6 个名额归共享调度，不空置等待目标账号 |
| 按需初始化或目标补池遇到繁忙自由槽 | 优先停止向该槽追加租约，完成在途请求后关闭并换入 |
| 连续真实请求需要不同账号 | 允许原有按需置换，无新增驻留时间、节流或创建销毁上限 |
| 恢复真实混合流量后持续运行 | 观察覆盖恢复过程、排队等待和初始化产出，不以暂停入口后的单次达标代替验收 |

持续运行验收应记录目标、真实覆盖、符合资格的冷账号数、排队量、初始化成功后的覆盖贡献、置换次数及等待时间。不能承诺在无合格账号、所有容量均有未完成长请求等条件下即时达标，但必须能解释阻塞原因，并在条件恢复后继续推进。

## 7. 建议增加的诊断日志

每次初始化、置换和跳过决策，建议记录：

- 初始化来源和真实请求模型，以及本次拟改善的模型目标。
- 账号内部索引、各相关模型的资格判断与覆盖贡献。
- 目标覆盖的 ready / initializing / deficit，以及计划换入换出后的变化。
- 总占用、自由/共享名额、总上限、初始化并发、关闭和容量预留状态；历史 `background_capacity=M-1` 不再作为最新容量规则。
- 排空原因、停止追加租约状态、置换候选和暂时无法推进的具体原因。
- 决策/初始化关联 ID，便于把“某账号 3.8 不可用但仍被初始化”追溯到实际入口。

不要记录账号邮箱、Cookie、API Key、代理凭据或完整上游敏感响应。以上字段是建议的观测能力，不是本日志已经实施的改动。

## 9. 后续修复记录（2026-10-25）

已按第 5 节实现主动覆盖选号、取消 M-1 物理后台上限、最多 M-1 个动态覆盖保护账号与共享名额优先排空。真实请求冷账号候选先比较目标贡献，普通池初始化机会优先推进可满足的覆盖计划；沿用既有创建、容量和延迟关闭机制。排空账号禁止追加租约，等待已有请求及消息队列结束后关闭；失效目标或取消需求会撤销尚未执行的排空。
