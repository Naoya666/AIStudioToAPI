# 按模型设置预热 Context 目标的改造讨论

日期：2026-10-24。最新需求澄清：2026-10-25。状态：已按最新规则完成本地实现与离线验证，尚未进行生产混合流量验收。第 9 节保留初版记录，第 10 节记录本次修改；最新规则与[主动协调问题日志](./model-context-warm-target-active-reconciliation-issue-20261024.md)一致。

## 1. 背景与用户目标

公益站同时开放热门模型、冷门模型和可用账号较少的模型。管理员希望依据已有的账号权益检测、人工层级配置、模型准入配置和实际调用知识，调整预热池中的账号模型覆盖情况。

典型场景：

- 最少就绪 Context 配置为 12，同时开放热门的 3.8f 和冷门的 3.5f，希望池内保留更多仍可调用 3.8f 的账号。
- 4a 的有效账号较少，希望条件允许时至少维持一个可以调用 4a 的就绪 Context，减少请求到来后等待冷账号初始化的情况。
- 目标模型可用账号不足或额度耗尽时，剩余容量继续共享，不保留空位，也不阻止其他模型使用池子。

本文中的 3.8f、3.5f、4a 是讨论简称。实际配置必须使用项目规范化后的真实上游模型 ID，不根据简称猜测权限或创建别名。

## 2. 现有配置语义

### 2.1 请求执行分配与 Context 驻留是两件事

| 配置 | 现有职责 |
| --- | --- |
| `MAX_BROWSER_WORKERS` | 缓存 Context/page 的最大数量 |
| `CONTEXT_POOL_MIN_READY` | 具备驻留资格的账号范围内，后台维持的最少就绪 Context 目标 |
| `GLOBAL_MAX_CONCURRENCY` | 全局同时执行的租约上限，可以与 Context 数量不同 |
| `MODEL_WORKER_ALLOCATION` | 模型请求竞争执行机会时的最低保障和优先分配数量 |
| `MODEL_MAX_CONCURRENCY` | 模型执行并发硬上限 |

一个 Context 属于一个账号，可以服务多个模型，也可能承载多个并发请求。逻辑执行槽不等于账号数、Context 数或独立浏览器进程数。

### 2.2 “最低保障 / 优先分配数量”及默认 `0 / 1`

现有调度器按模型当前正在执行的请求数判断排队优先级：

1. 执行数低于 `min` 的模型。
2. 已达到 `min`，但执行数低于 `preferred` 的模型。
3. 已达到 `preferred` 的模型。

同级按请求入队顺序选择，且必须满足账号可用、Context 就绪和各项并发限制。最低保障不会抢占或中断已有请求。

没有显式配置的模型，后端快照和排队优先级默认显示、使用 `min=0, preferred=1`：没有最低保障级别的优先权；当前执行数为 0 时，有机会优先于已达到各自 preferred 的模型获得执行机会。

例如两个模型都是 `0 / 1`，3.8f 正在执行 8 个请求，3.5f 没有请求在执行，两者均有请求排队且具备派发条件，则下一次空闲执行机会优先给 3.5f。两者都达到 preferred 后，按同级入队顺序竞争。

- 动态分配开启时，preferred 不是并发硬上限，模型可以借用空闲容量。
- 动态分配关闭时，显式配置模型以 preferred 为执行上限；未配置模型按剩余共享容量计算静态上限，至少允许一个槽位竞争。不能仅凭快照中的默认 `0 / 1` 判断未配置模型的静态上限。
- 显式配置的 preferred 总和不能超过全局并发，且 `0 <= min <= preferred`、`preferred >= 1`。

所以，把 3.8f 的分配改为 `8 / 10`、3.5f 改为 `1 / 2`，只能改变请求执行分配，不能保证热池有 10 个仍可调用 3.8f 的 Context。该示例还要求全局并发至少为 12，并满足模型并发等校验，不是通用推荐值。

### 2.3 现有热池的不足

新增功能之前的热池根据账号驻留资格、真实请求需求及现有候选排序维护，不按模型配置最低覆盖数量。只要账号仍符合驻留条件，3.8f 已进入 429 冷却、3.5f 仍可用的账号就可能继续驻留。

现有代码还会考虑账号层级白名单、不支持状态、账号健康和禁用状态等限制，不能简化为“所有显示模型都 429 才会退出”。详见现有账号层级与热池文档。

## 3. 已确认的新增能力

增加独立的模型字段，界面名称建议为 **“预热 Context 目标”**。

含义：在账号资格、当前可用状态和池容量允许时，尽量维持至少指定数量、可以调用该模型的就绪账号 Context。

这是有条件满足的最低覆盖目标，不是专属名额、硬分区、模型并发上限或额度承诺。

| 模型简称 | 预热 Context 目标示例 |
| --- | ---: |
| 3.8f | 10 |
| 3.5f | 0 |
| 4a | 1 |

示例假设热池目标为 12，且最大 Context 数量允许容纳。具体规则：

1. **容量共享。** 一个 Context 可以同时计入多个模型的覆盖数，也可以正常服务其他允许的模型。
2. **0 表示不要求最低覆盖。** 不禁止调用，也不禁止支持该模型的账号进入热池。
3. **账号不足时自然降级。** 3.8f 只有 6 个可用账号时，尽量覆盖这 6 个，其余位置继续共享。
4. **没有可用账号时不留空位。** 4a 可用账号为 0 时，目标 1 不阻塞普通补池，不反复加载已知不可用账号。
5. **恢复后重新协调。** 额度恢复、权限变化或新增可用账号后，后台在容量允许时逐步补足覆盖。
6. **目标主动介入。** 有可用候选时主动补足模型目标，必要时允许牺牲其他模型的体验；不要求证明其他模型覆盖或额度不受影响。
7. **不中断已有请求。** 补足目标或调整分布只在安全的空闲置换边界执行，不关闭繁忙 Context。
8. **不绑定固定账号。** 可根据最新资格、冷却和覆盖情况更换承担目标的账号。
9. **保留共享名额。** 单模型目标必须小于最大 Context 数，自由槽可正常驻留、调用和置换，不要求保留物理空位，详见第 5.2 节。

单模型目标必须通过第 5.2 节的数值校验。多个目标可以共享同一 Context 的覆盖，不机械要求目标之和小于池容量。运行时仍须保留至少一个不受预热目标保护的共享名额；可用目标账号不足释放出的名额也归共享调度。多个目标冲突时尽力满足，不引入复杂的全模型无损替换算法。

## 4. 可用性的依据与边界

用户意图是利用已有预检知识进行人工调整，而不是要求每个模型都先经过新的强制生成测试。

实现时应复用现有账号层级、模型白名单、账号健康、禁用、认证有效性、模型 unsupported 和冷却状态。预检或人工配置说明的是本地准入依据，不保证上游当前真实剩余额度。

- 当前有效的 429、403 或临时错误冷却中的账号，不计作该模型当前可用覆盖。
- 人工层级和模型权限不能覆盖真实请求产生的冷却、账号禁用或明确不支持状态。
- 面板估算剩余额度与实际不可用状态分开处理，不能仅因估算为 0 就断言账号不可用。
- 不为满足目标自动发起额外生成请求验证额度。
- 不恢复旧版 Argon 强制权益预检或人工专用白名单方案；沿用当前通用账号层级和模型准入策略。

“从未实际验证、但按当前准入策略允许”的账号是否计入覆盖，以及是否区分“按策略可用”和“已有成功证据”，留待实现前细化。此前讨论中的严格已验证计数只是建议，尚未确认为要求，不应额外引入必须逐模型预检的门槛。

## 5. 后续实现建议与待定项

以下是实现方向，不代表本轮已经确定具体算法或配置接口。

- 配置独立于 `MODEL_WORKER_ALLOCATION`，建议按真实模型 ID 保存非负整数；未配置默认 0，保持原有共享行为。最终配置键名、持久化方式和生效时机待定。
- 补池优先考虑目标缺口，并优先复用能同时覆盖多个缺口的账号；剩余容量按现有共享策略选择。
- 按需初始化和目标补池需要腾位置时，优先排空自由槽；不要求替换对其他模型无损，不新增最短驻留时间、置换节流或创建销毁次数限制。
- 初始化中的账号可以参与“已安排补足”的计算以防重复初始化，但不能计入“当前就绪可用”的展示数。
- 与不同代理优先策略结合时，采用第 5.1 节已确认的顺序；具体排序算法仍待实现设计。
- 多模型目标冲突时采用简单、可解释的尽力调度；不新增人工优先级字段或全局最优分配算法。
- 模型目标主动推动补池与分布修正；普通补池可以使用共享名额，整体允许达到最大 Context 数，不再设 M-1 的后台物理容量上限。
- 真实请求的按需换入与覆盖保护冲突时，需避免把目标实现成禁止置换的硬约束，保证请求仍可利用共享池。
- 账号或模型状态变化、请求释放、初始化及关闭完成、服务启动和配置变化时触发合并协调；复用现有生命周期保护，避免重建循环。
- legacy 模式是否支持该配置需明确，建议第一版只作用于模型感知调度模式。

### 5.1 已确认：先满足模型覆盖，再考虑代理出口分散

用户提出：模型预热目标为 10，出口 A 有 10 个以上具备该模型可用额度的账号，出口 B 没有该模型可用账号，但有其他模型可用账号。

用户已确认模型预热需求优先于代理出口分散。目标理解为全池覆盖数，不平均拆成每个出口的配额。不同代理优先继续作为候选选择偏好，不应使不具备模型资格的账号计入覆盖，也不为了出口均衡而把本来可满足的模型目标主动削减。

- 最大池容量为 12、目标为 10 时，可以先由 A 提供 10 个覆盖，再由剩余后台预热容量按现有策略考虑 B 的其他模型账号；剩余共享名额可正常驻留和调用，不强制留空。
- 最大池容量为 10 时，不允许该模型目标填写 10，最大只能填 9，前后端均应校验。
- 若多个出口都有满足覆盖需求的候选，再在这些候选之间优先分散出口；覆盖已满足后的共享补池也沿用出口分散偏好。
- 后续出现只能由 B 处理的真实请求时，可以使用共享名额，池满时优先排空自由槽并按原有机制置换。

后台预热的已确认顺序为：先补模型覆盖缺口，在能够同样满足覆盖的候选之间应用出口分散偏好，再使用现有选择规则打破平局。覆盖已满足后的普通补池继续考虑出口分散，可以正常使用共享名额。不新增每出口强制保留名额。

### 5.2 已确认：自由槽是可正常使用的共享名额

用户已纠正初版“必须留出一个实际空位”的解释。自由槽的意义是配置防呆和灵活调度，不是限制后台只能创建 M-1 个 Context。新增功能之前，整个池子都按这种共享方式调度；新增功能后，除模型预热覆盖之外的名额继续沿用原有机制。

#### 配置防呆与自由名额

设 `M = MAX_BROWSER_WORKERS`，单模型目标为 T，前端保存、后端配置保存和启动加载都校验：

```text
0 <= T <= M - 1
```

下调 M 时联动校验，不静默截断。M=1 时目标只能为 0。该规则不等于后台总量上限为 M-1，也不等于存在永久空闲槽。

- M=12、目标为 10 且可满足时，其余 2 个名额按共享逻辑使用。
- M=12、目标为 11 且可满足时，至少保留 1 个共享名额。
- M=12、目标为 10，但只有 6 个目标可用账号时，尽量维持这 6 个，其余 6 个名额归共享调度。
- 一个 Context 可以贡献多个目标覆盖；多个目标不能把所有名额都变成不可自由置换的覆盖保护名额。至少保留一个共享名额，具体标识复用简单的运行时选择，不引入复杂的重叠分配求解。
- 自由槽不绑定固定账号，可以支持目标模型，也可以服务其他模型；不能仅按“是否支持任意目标模型”判定它是否自由。

#### 满池与优先排空自由槽

普通补池可以将自由槽正常预热，因此实际驻留允许达到 M。取消初版通过 `background_capacity=M-1` 强制空出实际容量的行为；该字段和界面说明需同步调整，不能继续把共享名额显示成不可用的容量。

请求按需初始化和模型目标补池需要腾位置时，均优先排空自由槽：空闲时可直接关闭；繁忙时停止向选中账号追加租约，等已有请求完成，再关闭并初始化新账号。不强制中断在途请求，也不只等它在持续流量中自然空闲。

自由槽优先是选择偏好，不是禁止原有按需置换其他 Context 的硬约束；没有合适自由槽时，继续按原有安全条件处理。目标补池也应主动纠正未达标的分布，不能因账号仍能服务其他模型而一直保留它，更不要求证明其他模型体验不受损。

后续请求需要不同账号时，可以立即按原有条件反复关闭空闲 Context 并新建，不增加驻留保护期、销毁延迟、置换节流或次数上限。请求完成后的生命周期沿用原有机制。总容量、初始化并发、在途请求保护、失败清理及请求取消和超时规则仍然生效。

### 5.3 已确认：统一普通池初始化选号，复用已有执行机制

当前触发来源包括启动/普通补池、真实请求按需初始化、模型目标补池、故障恢复以及代理配置应用等管理重建。权益检测的临时 Context 和登录浏览器属于独立用途，不作为模型覆盖补池候选。

普通池已有 `_startPooledContext`、`_getOrStartContextInit`、容量预留、同账号初始化去重及初始化并发限制；底层 `_createBrowserContext` 对创建阶段排队。这些机制继续复用，不额外开一条主动预热创建通道，也不为此次改造建立复杂的独立调度系统。

需要统一的是候选选择与初始化机会顺序：

1. 有可用账号能够补足模型缺口时，优先安排目标账号初始化；池满时主动腾位置，优先排空自由槽。
2. 请求需要冷账号时，在同样能执行该请求的候选中，优先选能补足模型目标的账号，再考虑出口及原有账号排序。
3. 目标已满足或没有合格目标候选时，继续原有共享按需和普通补池逻辑。其他模型确实需要专有账号时仍可通过共享机制进入，不将目标实现为调用禁令。
4. 故障恢复保留必要的恢复流程；恢复后补哪些普通池账号，尽量复用同一套选号规则，不要求所有专用管理和检测流程改造成模型补池。
5. 各来源不能按固定的 `demanded → coverageWarm → warm` 拼接顺序长期绕过目标；去重和并发控制解决资源准入，选号优先级负责执行管理员设置。

核心边界：管理员负责模型比例的取舍，系统主动执行设置。可以牺牲其他模型的体验，不增加“其他模型仍有充分覆盖才允许替换”的条件，不要求多步最优置换或全模型额度无损证明。

## 6. 界面与观测建议

配置说明建议：

> 账号可用且容量允许时，尽量维持指定数量可调用此模型的就绪 Context。同一 Context 可覆盖多个模型；可用账号不足时，其余容量继续共享。0 表示不设置预热覆盖目标。单模型目标必须小于最大 Context 数；至少保留一个可正常驻留、调用和置换的共享名额，目标账号不足时其余名额也归共享调度。

展示目标、当前就绪可用数和正在补足数量。例如“目标 10 / 当前可用 6”，可附账号不足、等待空闲容量或初始化中等原因。缺口是运行状态，不等于配置错误。

同时补充现有“最低保障 / 优先分配数量”的说明，解释默认 `0 / 1` 以及动态分配下 preferred 不是并发上限，防止将其误认为 Context 分配数。

## 7. 后续改造验收场景

1. 配置为空或所有目标为 0 时，保持原有共享池行为。
2. 账号和容量充足时，3.8f 目标 10、4a 目标 1 得到满足；多模型覆盖可以重叠。
3. 3.8f 只有 6 个可用账号时，尽量预热这 6 个，其余容量继续共享。
4. 4a 没有可用账号时，不留空位、不阻塞补池、不循环初始化；恢复后重新补足。
5. 4a 唯一可用 Context 也可以执行其他模型请求，不被解释为独占保留。
6. 池满时通过空闲置换调整分布，已有流式请求继续执行。
7. 多模型目标无法同时满足时尽力调度并显示缺口，不要求全模型无损；真实请求引起的合法置换不受额外节流限制。
8. 冷却、禁用、认证失效、层级或白名单变化后重算覆盖，不把不可用账号计入目标。
9. 初始化并发、Context 总容量、延迟关闭、初始化取消和晚到发布等现有边界不回归。
10. 不修改现有 min/preferred 的排队优先级、动态借用及并发上限语义。
11. A 出口具备目标模型账号、B 出口没有时，覆盖按全池统计；不虚报 B 的覆盖，不因出口均衡无故减少可满足的覆盖。
12. 覆盖条件相同的候选分布在多个出口时，保留不同代理优先策略；剩余共享容量也可以容纳其他出口账号。
13. 前后端均拒绝单模型目标大于等于最大容量；下调最大容量时重新校验；最大容量为 1 时仅允许目标为 0。
14. 全池繁忙时不中断请求，覆盖等待、释放后重试、取消和超时；持续高负载的公平性按最终排空方案验收。
15. 真实需求初始化和执行期间，后台目标补足不会抢回容量；请求完成后不增加额外保护期，后续请求可以立即按原有条件置换该空闲账号。
16. 全局最少就绪等于 M 且账号足够时，普通补池可以使用自由槽，允许就绪数达到 M，不再强制空一个物理槽位。
17. 按需初始化与目标补池均优先选择自由槽排空；自由槽繁忙时停止追加租约并等待已有请求完成。连续请求可正常关闭并新建，无额外驻留限制。
18. 初始化、关闭和容量预留并发时复用原有去重、容量与并发控制，不超限；所有目标为 0 时所有名额按原有共享逻辑使用。
19. 目标 10 但只有 6 个可用账号、M=12 时，另外 6 个名额均可共享；自由槽不绑定固定账号。
20. 混合流量下目标初始化主动推进，不要求证明其他模型无损；等价请求候选先比较目标贡献，再考虑代理出口。

## 9. 初版实现记录（2026-10-24，非最新改造要求）

本节记录已存在的初版行为。以下 M-1 物理后台上限、后台置换要求所有模型覆盖不下降等选择，已被 2026-10-25 的用户澄清取代，需按第 5 节修改；保留记录便于定位实现差异，不表示最新规则已经落地。

本次实现增加 `MODEL_CONTEXT_WARM_TARGETS`，JSON 对象按规范化后的真实上游模型 ID 保存非负整数。环境启动加载和统一配置保存均校验每项小于 `MAX_BROWSER_WORKERS`；通过统一配置持久化，重启生效。legacy 模式不应用目标。

计数采用当前策略准入：健康、未禁用、认证未过期、层级及白名单允许、未隐藏、无 unsupported 和有效冷却。无需逐模型成功记录或额外生成探测；执行中但仍可用的 Context 也计入覆盖，执行并发限制不影响覆盖统计。初始化和容量预留参与安排计数，独立于当前就绪数。所有类型冷却到期均唤醒协调。

模型覆盖可主动提高普通最少就绪目标，但模型补池与普通补池共同受 M - 1 后台容量上限限制；容量统计复用驻留、初始化、同步容量预留和未完成关闭的并集。真实需求可使用第 M 个容量。真实请求完成后不增加额外保护期。

补池贪心选择同时缩小最多模型缺口的账号，同分时沿用不同代理优先和现有账号顺序。已安排初始化参与缺口计算。后台置换仅选择空闲 Context，且要求各模型截断到目标后的覆盖均不下降、至少一项严格上升；无法安全改善时保留当前分布并显示缺口，因此冲突目标不会无限互换。本版不新增人工优先级、驻留时间或置换节流。真实请求置换优先选择损失覆盖较少的空闲账号，但所有空闲账号仍可被真实请求置换。

调度快照每模型增加 `warm_contexts`（`target`、`ready`、`initializing`、`deficit`），池快照增加 `background_capacity`。配置界面提供输入上限和联动校验；调度面板显示覆盖缺口、补足中数量与后台容量说明。全局 `effective_warm_target` 继续展示受后台容量和驻留资格限制的普通补池目标，各模型覆盖独立展示。

## 10. 主动协调与共享名额实现（2026-10-25）

取消 M-1 后台物理容量限制，`background_capacity` 现为 M，普通补池可达到 M。单模型配置仍校验 `0 <= T < M`。

普通池使用简单的贪心覆盖计划：按模型目标贡献选择最多 M-1 个覆盖保护账号，相同贡献优先复用已驻留或正在初始化的账号，再考虑出口分散和原有账号顺序。保护身份按当前状态重新计算，不按账号是否支持任意目标模型划分自由身份；候选不足时保护账号数量自然减少，其他名额均可共享。互相冲突的目标尽力满足，偏好现有账号保持稳定，不增加人工优先级或全模型无损证明。

目标计划中的缺口候选先于无目标贡献的请求需求和普通补池获得初始化机会。请求冷账号候选也先比较当前目标贡献，再比较出口及原有顺序；恢复后普通补池复用相同入口。所有普通初始化继续经过原有去重、容量预留、初始化并发控制和底层创建队列，不新增创建通道。权益检测和登录浏览器不参与目标覆盖。

满池时目标补池与按需初始化优先选择不在当前保护计划中的共享账号。空闲时沿用原有关闭置换；繁忙时标记排空、停止所有模式下的新租约、保留已有请求，复用现有延迟关闭与队列排空事件完成关闭。一次只推进一个置换；该限制仅复用已有关闭生命周期串行保护，不增加时间节流或次数限制。目标候选失效或请求取消/超时后撤销尚未执行的排空，保留后续禁用或故障排空的独立状态。

快照增加 `protected_contexts`、`shared_contexts`、`shared_minimum`，界面展示当前覆盖保护和共享驻留数量。`shared_minimum` 表示共享名额要求，非实际空位承诺。覆盖的 ready / initializing / deficit 保留原语义。

离线测试补充满 M 修复、持续混合需求与繁忙账号排空、取消和冷却变化清理、目标贡献优先于请求入口及代理偏好、目标不足时释放共享名额、多目标冲突稳定性和总容量检查。生产运行中的吞吐、排队等待和长期覆盖恢复仍需实际部署后采样验证。
