# 不同代理优先调度改造方案

## 1. 文档状态与目标

- 状态：已实现，部署后仍需使用真实代理和账号验收。
- 日期：2026-10-24。
- 新增模式：不同代理优先，配置值 `different_proxy_first`。
- 实现与验收依据：本文；运行说明见 [模型感知调度](./model-aware-scheduling.md)。

目标是让请求尽可能分散到多个代理出口，同时沿用现有多 worker、账号 × 模型调度架构。当当前请求只有一个可立即调度的出口时，在该出口内回退到“较久未使用优先”。

分散对象包括串行请求的出口选择和并发请求的在途分布。请求耗时、Token 数量不同，因此不承诺出口之间的实际流量字节数完全均衡。

## 2. 改造前实现与保留约束

改造前 `ACCOUNT_ROTATION_STRATEGY` 支持 `least_recently_used`、`least_used` 和 `legacy`。前两者使用 `ModelScheduler`，旧版模式继续使用原账号切换流程。

现有模型调度的账号选择先筛选可用且就绪的 Context，再依次比较：账号 × 模型在途数、账号总在途数、近期本地传输失败、策略相关计数、账号 × 模型最近使用时间和选择顺序等。

Worker 是逻辑执行槽，可复用账号 Context；后台 Context 数量受 `MAX_BROWSER_WORKERS` 限制，全局租约数另受 `GLOBAL_MAX_CONCURRENCY` 限制。新模式继续遵守这些限制以及模型配额分配、账号和 Context 并发限制。

账号代理在 Context 创建时应用。`ProxyBindingService` 已区分期望节点和当前应用节点，Context 的 `proxyInfo` 记录当前使用的代理信息。代理来源还包括旧代理文件、环境变量和直连，不能仅覆盖 Mihomo 节点池。

相关现有说明：

- [模型感知调度](./model-aware-scheduling.md)
- [代理池设计](./mihomo-proxy-pool-design.md)

## 3. 范围与基本原则

1. 新增调度模式，不改变其他三种模式的选择语义。
2. 账号 × 模型继续保存权限、不支持、429、冷却、用量等状态；出口组只承担负载排序和观测。
3. 模型间 worker 分配、队列公平性和请求预算沿用现有机制；在选定待处理请求后才进行出口和账号选择。
4. 不为每个请求修改账号绑定，不为轮换出口频繁重建 Context，不中断在途请求。
5. 代理绑定失效时沿用现有错误处理，不静默切换直连。
6. 本期不增加出口硬并发上限、出口级额度、自动代理故障转移或出口级 403/429 封禁。

## 4. 出口组身份

### 4.1 分组规则

出口组是调度维度，用于表达多个账号或代理节点共享同一出口。建议由统一的出口身份解析模块生成内部 `egressKey`，供调度器、热池和状态接口共同使用。

| 来源                       | 默认分组规则                                     |
| -------------------------- | ------------------------------------------------ |
| Mihomo 远程节点            | 按稳定节点 ID 分组，不按本地 SOCKS 监听端口分组  |
| 旧代理文件、环境变量代理   | 按规范化的代理路由身份分组；相同路由应得到相同键 |
| 默认直连、直连节点         | 统一归入 `direct` 组                             |
| 配置了共享出口组的远程代理 | 以显式配置的出口组作为分组依据                   |

第一版包含可选的手工出口分组：节点可填写出口组，同组节点共享调度计数；未填写时使用默认规则。旧代理来源应保留同等分组扩展入口，避免两套路由来源无法表达共享出口。组名需去除首尾空白、限制长度，空值代表使用默认分组；内部键使用命名空间避免与节点 ID、直连键冲突。

代理路由身份不得只比较服务器域名或 IP：端口、协议以及认证或会话配置可能对应不同路由。内部可通过规范化后摘要生成键，不向管理 API 或日志输出凭据或原始代理 URL。不同来源解析到同一路由时应尽量统一身份；无法可靠确认时，允许使用显式出口组归并。

不同代理节点不一定对应不同公网 IP。管理页已有出口 IP 测试结果，可用于提示可能共用出口，但本期不根据探测结果自动合并或拆分组。动态代理、IPv4/IPv6 路由差异和探测结果过期，都可能使观测 IP 与实际业务出口不同。

### 4.2 当前身份与预期身份

- 已有 Context：按该 Context 实际应用的代理及分组版本确定身份。
- 尚未创建的 Context：后台规划可读取期望代理身份，但发布为就绪 Context 时必须重新确认实际身份。
- 修改账号绑定但尚未应用：现有 Context 继续使用旧组；重建完成后才进入新组。
- 修改节点出口组：按现有代理配置应用流程排空并应用分组快照，避免仅修改配置就使旧 Context 的归属漂移。
- 创建租约时保存不可变的 `egressKey`；释放时使用租约快照，不重新解析当前配置。

分组快照使用解析后的不可变出口键区分分组配置；只有当前与期望出口键一致，才认为分组已经应用。运行中的旧租约和新 Context 即使分属不同组，也应分别准确记账，旧组在不再被引用后才可回收。

## 5. 调度规则

### 5.1 候选过滤

先执行现有过滤：账号健康、人工禁用、模型权限、不支持与冷却、重试账号排除、文件归属、Context 可租用状态以及各级并发限制等。

出口偏好只能作用于过滤后可立即获得租约的账号。节点池中存在节点，不等于该节点对当前模型存在可调度账号。非默认配置允许非就绪 Context 参与时，继续遵守现有准入规则，并在租约创建前取得一致的代理身份快照。

### 5.2 出口排序

将候选账号按 `egressKey` 分组，按以下顺序选择出口：

1. 本次请求尚未尝试过的出口优先，仅重试阶段适用。
2. 出口跨模型总在途租约数较少者优先。
3. 在途数相同，较久未被选择的出口优先。
4. 再相同，以稳定内部键打破平局，保证结果可复现。

出口总在途数统计服务内所有相关模型租约，包括非模型文件操作租约；不按出口下账号数量加权。出口轮换是跨模型的，因为需要分散的是共享出口的请求。

使用单调递增选择序号记录出口选择先后，避免同毫秒选择和系统时钟调整影响公平性。新组按从未选择处理；序号相同时使用稳定键排序。

### 5.3 组内账号排序

在选中的出口组内复用现有 `least_recently_used` 完整排序：

1. 账号 × 当前模型在途数。
2. 账号总在途数。
3. 近期本地传输失败次数。
4. 账号 × 模型最近使用时间。
5. 最近选择序号与账号索引等现有平局规则。

不要把“较久未使用优先”简化为只比较一个时间戳。其他模式仍使用原比较顺序，新出口规则不插入其排序链。

### 5.4 回退与等待

| 当前请求的状态                       | 行为                                     |
| ------------------------------------ | ---------------------------------------- |
| 两个及以上出口有可租用账号           | 按出口排序，再按组内账号排序             |
| 只有一个出口有可租用账号             | 直接在该组内按现有 LRU 规则选择          |
| 其他出口尚未就绪                     | 当前可调度请求继续执行，后台补充出口覆盖 |
| 没有可立即租用的账号，但仍有合格账号 | 沿用现有排队、后台准备及超时流程         |
| 没有符合资格的账号                   | 沿用现有无可用账号错误和重试错误保留规则 |

不为等待不同出口而额外阻塞已有可用账号的请求，不绕过任何额度、冷却、并发或文件归属限制。

### 5.5 示例

账号 A、B、C 属于 P1，D 属于 P2，E、F 属于 P3。三个出口都空闲且可调度时，连续串行请求倾向于在 P1、P2、P3 之间轮换；组内账号由 LRU 规则选择。

若在途数为 P1=4、P2=1、P3=1，优先从 P2、P3 中选择较久未被选中的组。即使 P1 下有更多空闲账号，也不因此优先选择 P1。

若 P2、P3 对当前模型都不可用，则请求在 P1 的合格账号间按 LRU 分配；它们对其他模型是否可用，不改变当前请求的候选集合。

## 6. 租约、计数与并发一致性

建议出口运行态至少包含 `inflight`、`lastSelectedSequence`；租约增加出口身份快照。出口在途数表示已预留执行资源的租约数，不表示已成功发送或成功完成的请求数。

账号选择、出口计数预留、账号与模型计数预留、worker 租约绑定必须在同一同步临界流程中完成，中间不插入 `await`。同一轮为多个 worker 分配时，后一次选择必须看到前一次增加的出口在途数。

所有释放路径都通过现有幂等释放入口扣减出口计数，包括正常完成、未发送即失败、取消、传输故障、超时、恢复和关闭。重复释放不得造成负数；释放只使用租约保存的键。

出口运行态不写入 `scheduler-state.json`，进程重启后在途数从零开始，选择顺序重新建立。现有账号 × 模型持久化不变。每日冷却重置不清除活动出口在途数。

保证范围沿用当前单服务进程；本期不实现跨实例出口负载协调。运行态回收不能删除仍被 Context 或活动租约引用的组，也不能在普通空闲时立即抹掉轮换历史。

## 7. 后台热池与出口多样性

只修改最终账号排序不足以达成目标：如果驻留 Context 全部属于 P1，就绪候选永远无法覆盖 P2、P3。必须同时修改后台候选与置换排序。

### 7.1 预热候选

- 先保留现有明确请求需求及模型资格规则。
- 在相同需求等级内，优先选择尚无可用驻留 Context 的出口，再补充已有出口内的账号。
- 已被接纳初始化的 Context 也计入规划覆盖，避免并行初始化反复选择同一出口。
- 预热受 `CONTEXT_POOL_MIN_READY`、Context 容量和初始化并发限制，不强制为所有出口创建 Context。
- 针对排队模型选择账号时，应比较该模型的有效覆盖，不能因某出口存在仅支持其他模型的 Context，就认为当前模型已被覆盖。

### 7.2 满池时的补充与置换

热池已满但某些可用出口未覆盖时，后台应能触发有界的多样性修正，不能只在“没有 ready 账号”时才提出冷账号需求。

在模型需求、健康及驻留资格规则满足后，优先用未覆盖出口的合格账号替换重复出口中的空闲 Context。置换不能移除满足当前明确模型需求的唯一可用 Context，也不能破坏现有配额淘汰和需求优先级。

采用单次规划去重和置换防抖；只有预计增加有效出口覆盖时才为多样性执行置换。已有需求引发的正常置换仍遵循原规则。所有 Context 都在忙时，不仅为增加出口覆盖而主动排空账号；等待自然空闲机会，原有必须满足模型需求的排空流程保留。

当可用出口数超过热池容量时，不要求所有出口轮流驻留，不因存在更多出口持续换入换出。第一版保证容量范围内的覆盖与分散，公平性主要针对当前可调度出口。

`MAX_BROWSER_WORKERS=1` 时不为多样性反复换 Context；需要更多同时驻留的出口，应增加 Context 容量。初始化失败继续使用现有退避，不能形成高频重试循环。

## 8. 重试与错误处理

`ScheduledRequestHandler` 继续维护本次请求已尝试的账号，增加已尝试出口集合。在实际开始上游尝试时记录租约出口；仅取得后取消、未发送的租约不标记为已尝试出口。

重试时，已尝试账号仍是硬排除条件；已尝试出口是软偏好。存在未尝试过且可立即租用的出口时优先选择，否则允许同出口的其他合格账号，避免不必要地结束重试或等待。

将出口偏好作为可选的请求调度上下文传入，不将出口键混入现有账号排除集合。保持原有最大重试次数、发送前检查、文件账号亲和性以及已输出流内容后不重放的限制。

普通 429、403、上游 5xx 和本地传输故障继续按现有作用域处理，不因两个账号共用出口就自动批量冷却整个组。代理本身不可用时依照现有代理和 Context 可用性机制处理。

## 9. 配置、界面与观测

新增配置：

```dotenv
ACCOUNT_ROTATION_STRATEGY=different_proxy_first
```

新模式启用模型调度器，配置生效时机沿用现有调度模式设置，不另外引入模式热切换。默认值仍为 `least_recently_used`。

管理界面新增选项“不同代理优先”，说明建议为：

> 优先使用在途请求较少、较久未使用的代理出口；仅一个出口可用时，按较久未使用优先选择账号。

节点编辑增加可选“出口组”，说明同公网出口的节点可填写相同组名。直连始终归入统一组；修改分组应显示待应用状态，并通过现有应用流程生效。

调度快照建议增加：

- 当前策略及出口组汇总。
- 每组总在途数、就绪可租用账号数、最近选择顺序。
- 每模型可立即调度的出口组数量，用于解释为何某模型只能使用一个出口。
- 聚合的单出口回退次数与多样性置换次数，便于确认策略效果。

就绪可租用账号数要注明其模型和并发判断口径，不能将单纯 `READY` 数冒充当前模型可租用数量。出口级租约在途总数应与活动租约总数一致。

运行日志使用内部安全标识或显示名称，不输出认证配置。复用现有状态接口和刷新链路，本期不增加逐请求永久审计库或高频日志。

以下为实现定位。出口身份与比较规则集中实现，避免各调用方自行推导。

| `src/core/SchedulerConfig.js`                          | 接受新模式，继续开启模型调度                               |

旧数据缺少出口组字段时使用默认分组，无需修改账号认证文件。其他三种模式忽略新增的出口调度偏好；共享出口组配置不得改变实际代理连接参数。回滚时需确认新增可选字段能够被旧版本容忍，并先将调度策略改回旧版本支持的值。

## 11. 验证与验收标准

新增 `tests/different-proxy-first.test.js`，并扩展现有请求与浏览器热池回归。相关基线包括 `tests/model-scheduler.test.js`、`tests/browser-workers.test.js`、`tests/scheduled-request.test.js`、`tests/proxy-pool.test.js` 及相关配置和界面测试。使用模拟账号、Context、代理和时钟验证规则，无需向 Google 发请求验证排序。

必须覆盖以下行为：

1. 多个空闲出口的串行请求按出口选择顺序轮换，账号数量不改变出口权重。
2. 单轮多个 worker 的选择能看到前序预留；并发优先分配到较低出口负载。
3. 不同模型共享出口负载，同时保持各自账号 × 模型冷却和模型队列公平性。
4. 单出口结果与原 LRU 选择一致；零候选保持现有排队和错误语义。
5. 其他出口未就绪时立即使用现有候选，同时后台补充覆盖，不等待代理轮换。
6. 多个节点显式同组后共享负载；直连来源统一分组；代理文件和环境变量路由得到稳定身份。
7. 修改期望绑定、节点出口组或删除配置后，旧 Context 和活动租约仍按原快照正确释放，新 Context 使用应用后的身份。
8. 完成、失败、取消、重复释放、浏览器恢复和服务关闭后计数不泄漏、不为负，出口在途总数与活动租约一致。
9. 重试优先未尝试出口；只有同出口其他账号时仍可重试；文件亲和性和流式输出约束不被绕过。
10. 热池覆盖考虑初始化中的账号及模型资格；满池重复出口可被安全修正，唯一需求出口受到保护。
11. 忙 Context 不因单纯多样性被排空；容量小于出口数、单 Context、代理初始化失败时均不形成置换或初始化循环。
12. 既有三种模式、旧配置缺省行为、配置保存和状态 API 保持兼容；输出中不包含代理凭据。

实施后按项目现有检查要求运行相关测试、完整测试、lint 和 UI 构建：

```bash
npm test
npm run lint
npm run build:ui
```

部署验收建议准备三个已确认不同出口、各有有效账号的节点，观察串行轮换和并发在途分布；再让两个节点显式同组，验证组内记账和选择。随后验证单出口可用、某模型仅一个出口有资格、绑定待应用与应用后重建等情况。
