# 不同代理优先：Context 分散方案与性能修复

## 1. 当前方案

2026-10-24 修订。本方案替代最初的逐请求出口轮换方案。

目标是**创建和补充 Context 时尽量分散代理出口，请求继续使用现有 LRU 调度**。配置值保持 `different_proxy_first`，管理页继续显示“不同代理优先”，说明文字明确它作用于 Context 分布。

高流量下，请求会随可用 Context 和现有在途数均衡自然分布；低流量下不追求严格的出口轮换。实际分布受账号 × 模型资格、冷却、并发限制及请求耗时影响，不承诺各出口请求数、Token 或字节数相等。

本次只修改项目源码、测试和文档；生产部署需要另行执行。

## 2. 原实现的问题及修复边界

原实现将出口偏好同时放入候选筛选、请求排序、重试和主动 Context 置换。在 218 个账号、12 个就绪 Context 的规模下，每次就绪候选查询会额外解析 206 个冷账号的代理；完整检查 40 个等待请求会重复 8,240 次。

第一次部署中，每次代理解析深拷贝整个代理池，导致严重阻塞。后续 `snapshotForAccount` 将其缩小为单账号快照，但重复解析、分配和克隆次数没有减少。需求扫描位于实际派发之前，会耗尽每轮 8ms 预算；下一轮再做相同扫描，造成有就绪 Context、无活动租约却持续排队的调度饥饿。

修复同时处理计算量和推进顺序：

- 删除请求级出口排序、出口租约计数和最近选择历史。
- 删除请求级“已尝试出口”集合，重试沿用原账号排除规则。
- 删除纯粹为增加出口覆盖而进行的主动换入、排空和置换。
- 请求派发不解析冷账号代理、不深拷贝代理池。
- 结构性就绪候选在同一同步轮内按模型复用，实时检查每次租约改变的并发状态。
- 冷账号需求检查移到合并的后台回调，使用独立时间预算，不阻塞就绪请求的派发。
- 热池规划一次计算驻留资格和出口占用，不在候选循环中反复重建模型集合与覆盖集合。

## 3. 请求与重试

`different_proxy_first` 的账号排序与 `least_recently_used` 相同：

1. 账号 × 当前模型在途数较少。
2. 账号总在途数较少。
3. 近期本地传输失败较少。
4. 账号 × 模型较久未使用。
5. 最近选择序号和账号索引等原有平局规则。

权限、人工禁用、登录状态、模型不支持、429/403 冷却、全局和各级并发限制继续由原调度器执行。文件归属仍是硬约束。上游已输出内容后不重放请求。

重试继续排除本次请求已尝试的账号。同一出口的其他合格账号可以立即使用，不等待不同出口，也不单独计算出口偏好。

每轮只复用结构性资格和就绪候选；账号/模型 inflight、Context 并发上限、排空状态和请求排除条件仍在租用时检查，避免缓存导致超额派发。缓存随同步轮结束丢弃，不引入跨轮资格缓存或额外配置失效机制。

`least_used`、`legacy` 的策略含义保持不变。通用的后台需求调度和单轮候选复用不改变模型队列优先级、worker 分配或冷却语义。

## 4. Context 创建与补充

### 4.1 什么时候选择出口

仅在以下情况需要创建或替换 Context 时执行出口分组：

- 启动预热或热池低于既定就绪目标。
- Context 关闭、失效、淘汰后正常补充。
- 现有调度逻辑发现某个请求需要尚未驻留的账号。

已有健康 Context 正常复用。满池时不因为出口分布不均衡而主动置换，不因出口数量超过容量而持续轮换。

### 4.2 如何选择账号

先执行原有驻留资格、模型资格、请求账号排除、初始化退避和容量规则。明确的请求需求仍优先于普通预热。

对同一批待创建候选：

1. 从已有 Context 和已接纳初始化任务计算各出口的驻留数量。
2. 将合格候选按出口分组；每个账号在本次规划中最多解析一次路由。
3. 优先选择驻留数量最少的可选出口；相同数量按候选原顺序选择。
4. 每选中一个账号就增加该出口的规划数量，保证批量预热也能分散。
5. 单出口时直接沿用候选顺序，不增加等待。

初始化中的账号也计入规划，避免并行任务重复集中在一个出口。只有需要新建 Context 才做上述路由解析；就绪目标已经满足且没有冷账号需求时，不解析冷账号代理。

出口选择不更改账号绑定。被绑定的代理不可用时沿用既有失败与退避规则，不静默直连。

### 4.3 模型和容量边界

冷模型请求的候选先按该模型资格筛选，再在候选出口中选择。正常预热保持原有跨模型驻留资格规则，不计算额外的逐模型出口覆盖修正。

当模型资格变化导致当前 Context 无法服务时，仍可由原有请求需求触发必要的空闲 Context 置换；忙 Context、明确的模型需求和排空规则继续由现有容量机制保护。

`MAX_BROWSER_WORKERS=1` 时复用单 Context，不为轮换出口重建。出口数多于容量时，只在正常生命周期中调整分布。初始化失败不引入新的紧密重试循环。

## 5. 出口身份与配置应用

保留统一的 `ProxyEgressIdentity` 以及已有的可选出口分组：

| 代理来源                 | 默认分组                                       |
| ------------------------ | ---------------------------------------------- |
| Mihomo 远程节点          | 稳定节点 ID                                    |
| 旧代理文件、环境变量代理 | 规范化路由身份的摘要，包含协议、端口和认证差异 |
| 默认直连、直连节点       | 统一 `direct`                                  |
| 显式配置出口组的代理     | 使用该组；账号出口组覆盖节点默认组             |

不同节点不必然对应不同公网 IP。管理页测试结果供参考，不自动合并或拆分组。代理凭据不输出到调度状态或日志。

已有 Context 使用当前实际应用的代理快照。修改绑定或出口组后，管理页显示待应用；按原有应用流程排空并重建，才改变 Context 的分组。后台规划冷账号可以读取期望配置，实际创建仍通过原代理解析与校验流程。

`snapshotForAccount` 保留，避免需要创建 Context 时读取路由又深拷贝整个代理池；不引入跨配置版本的路由缓存。

## 6. 管理界面与兼容

```dotenv
ACCOUNT_ROTATION_STRATEGY=different_proxy_first
```

默认值继续为 `least_recently_used`。调度模式保存后按现有重启流程生效。现有账号、代理节点、出口组、认证文件和账号 × 模型持久化数据不需要迁移或清零。

界面说明：

> 新建和补充 Context 时按出口分散；请求沿用较久未使用优先，不逐请求轮换出口。

管理调度快照中的出口统计改为从现有 Context 推导：

- `groups[].contexts`：驻留 Context 数。
- `groups[].ready_contexts`：Context/page/连接就绪数，包含正在处理请求的 Context。
- `groups[].inflight`：现有账号租约的在途数之和，只作观测。
- `by_model` 和 `models[].ready_egress_groups`：该模型当前具备合格、就绪且满足账号/Context 并发条件的候选出口，不表示全局执行槽一定有空余。

统计只读取现有 Context，不解析冷账号代理。删除原请求级 `lastSelectedSequence`、`ready_accounts` 组汇总及回退/主动均衡置换计数；这些临时管理统计不再表示新方案的行为。API 协议转换、公开看板协议和模型错误作用域保持不变。

## 7. 主要实现范围

| 模块                                    | 内容                                                             |
| --------------------------------------- | ---------------------------------------------------------------- |
| `ModelScheduler`                        | LRU 请求选择、单轮候选复用、独立后台冷需求回调；移除出口租约状态 |
| `ScheduledRequestHandler`               | 普通账号排除重试，移除出口历史                                   |

| 测试、基准脚本与运行说明                | 覆盖大账号池推进能力和代理读取次数                               |

## 8. 验证与性能门槛

必须覆盖：

1. 同一组就绪账号、相同模型状态下，新模式与 LRU 的请求选择结果相同。
2. 重试允许同出口的其他账号，继续遵守模型冷却、并发上限及文件账号归属。
3. 就绪请求派发、释放、恢复和状态统计不解析冷账号代理。
4. 预热和补充优先驻留较少的出口，包含已接纳初始化任务；单出口、代理不可用、初始化退避正常。
5. 满池且没有冷账号需求时，保持现有 Context；不触发路由扫描或纯均衡置换。
6. 冷模型需求在后台准备，热模型先获得可用租约，原有必要置换与初始化生命周期不回归。
7. 218 账号、12 就绪 Context、5 出口下，40/300/1000 个排队请求持续推进、无调度超时、无冷代理读取。
8. 配置应用前后继续区分当前与期望出口组，不自动修改账号代理。

执行：

```bash
npm test
npm run lint
npm run build:ui
node scripts/bench/context-spread.js
```

基准比较相同合成场景下 LRU 与新模式的派发耗时、冷代理解析次数、快照次数及满池规划开销。时间用于趋势比较，不能替代生产压测；测试以零额外冷代理读取和持续派发作为结构性约束，不采用容易受 CI 负载影响的微秒级断言。

部署后仍需检查真实请求成功率、事件循环延迟、CPU、队列等待、正常 Context 补充频率和各模型可用出口分布。不得通过清除冷却或重置账号状态强行通过验收。
