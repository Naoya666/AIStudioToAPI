# 账号层级模型白名单改造方案

日期：2026-10-20。状态：已完成代码实现和本地验证。需求与验收标准保留如下，实际操作见第 11 节。

## 1. 背景与目标

项目已有 Free、Pro、Ultra 5x、Ultra 20x 账号层级，以及手动层级和上游权益检测机制。目前模型准入主要对 `gemini-4-argon` 做专用付费判断，不能配置其他模型的层级限制。

本次将其扩展为统一的“账号层级 → 模型白名单”策略，并提供后台配置入口。目标是让已知受限模型只分配给允许的账号，减少无效调用，同时避免管理员逐个测试现有模型后才能开放服务。

核心原则：**首次初始化批量开放现有模型，仅从 Free 白名单中移除已确认的三个付费模型；后续新增模型由管理员显式配置允许的层级。**

本文延续 [账号层级、付费权益检测与 Argon 调度改造方案](./account-tiers-and-argon-eligibility-design.md) 中的账号层级和状态独立保存规则；涉及模型准入时，以本文的通用白名单方案替代原来的 Argon 专用规则。

## 2. 已确认的初始权限

| 模型范围                         | Free   | Pro  | Ultra 5x | Ultra 20x |
| -------------------------------- | ------ | ---- | -------- | --------- |
| `gemini-3-flash-preview`         | 不允许 | 允许 | 允许     | 允许      |
| `gemini-3.6-flash`               | 不允许 | 允许 | 允许     | 允许      |
| `gemini-4-argon`                 | 不允许 | 允许 | 允许     | 允许      |
| 首次初始化时模型列表中的其他模型 | 允许   | 允许 | 允许     | 允许      |

依据与边界：

- 用户实测，上述三个受限模型在 Free 不可调用，在 Pro 可以调用。
- 用户已测试 `gemini-3.1-pro`、`gemini-3.5-flash`、`gemini-3.7-flash`、`gemini-3.8-flash` 可以调用，初始向所有层级开放。
- 其他现有模型尚未逐一测试，但按已确认的维护策略，初始同样向所有层级开放；“配置允许”不等于已经通过上游实测。
- 当前没有 Ultra 账号可测试，因此 Ultra 两档初始复制 Pro 的模型权限；这是暂定策略，不是已验证的上游权益结论。
- 四个层级独立保存白名单，后续可分别调整；不强制层级继承，也不持续自动同步 Pro 与 Ultra。

### 2.1 精确模型 ID

权限按规范化后的完整模型 ID 匹配，不能因为名称中含有 `pro`、`flash` 或某个版本号就推断权益。

当前 `configs/models.json` 中存在 `gemini-3.1-pro-preview`，用户测试时使用的描述为 `gemini-3.1-pro`。实现时应核对现有入口是否存在对应别名，不能擅自认定两者相同，也不因该名称差异阻塞初始化：当前列表中的该模型仍属于“其他模型”，向所有层级开放。

## 3. 账号层级解析

沿用 `AccountTierPolicy.resolveTier()` 的现有规则：

1. 手动层级非空时，优先采用手动层级。
2. 否则采用当前会话有效的权益检测结果：`ready-free` 对应 Free，符合现有条件的 `ready-paid` 对应 Pro。
3. 没有有效结果时，账号层级为未知。

未知账号查权限时使用 Free 白名单，但存储和界面仍显示“未知”，不能写回为 Free。上游检测不能推断 Ultra 两档。

手动声明、上游观察、账号与模型的调用状态继续独立保存。手动设置付费层级只改变本地准入，不伪造上游权益或认证信息。

## 4. 白名单配置与生命周期

### 4.1 数据模型

建议保存带版本的结构化配置，包含四个层级的完整模型 ID 数组。以下为结构示例，省略了其他现有模型，不能直接作为完整初始配置：

```json
{
  "version": 1,
  "tiers": {
    "free": ["gemini-3.5-flash"],
    "pro": ["gemini-3.5-flash", "gemini-3.6-flash", "gemini-4-argon"],
    "ultra": ["gemini-3.5-flash", "gemini-3.6-flash", "gemini-4-argon"],
    "ultra20": ["gemini-3.5-flash", "gemini-3.6-flash", "gemini-4-argon"]
  }
}
```

接入现有统一配置服务的读取、校验、保存与运行时应用流程。具体配置键和持久化位置在实现时按现有架构确定，避免新增互相覆盖的多个配置来源。

校验要求：

- 四个层级字段齐全，值必须为模型 ID 数组；空数组表示该层级不允许任何受本策略管理的模型。
- 使用统一模型规范化逻辑并去重；拒绝非法 ID、未知层级及通配符。
- 正常编辑仅允许选择已登记模型；初始化时保留三个已确认受限 ID 的权限规则，避免因本地列表暂缺该模型而丢失约束。
- 配置不存在与配置为空必须区分，不能把管理员保存的空白名单当成未初始化。
- 损坏或版本不支持的配置应报错，保留当前有效配置；启动阶段不得静默回退为全开放。

### 4.2 首次初始化与迁移

仅在没有白名单配置时执行一次：

1. 读取当前有效模型目录，排除 `__files__` 等内部操作标识以及请求修饰产生的虚拟名称。
2. 将该目录内所有模型加入四个层级的初始白名单。
3. 从 Free 中移除 `gemini-3-flash-preview`、`gemini-3.6-flash`、`gemini-4-argon`。
4. 确保 Pro 和 Ultra 两档包含上述三个受限 ID。
5. 原子保存配置和版本，再投入调度使用。

初始化必须幂等。重启、升级、重新读取模型列表时，不得再次批量开放，也不得覆盖管理员已经修改的权限。已有隐藏模型仍保持隐藏；进入白名单不代表自动取消全局禁用。

### 4.3 后续新增模型

首次初始化完成后，不再将新模型自动加入所有层级。新增模型时应在同一管理流程中选择允许的层级，提供“全部层级”快捷勾选，保存后写入相应白名单。

如果通过文件直接新增模型但未配置权限，该模型保持未授权，并在后台提示待配置。管理员可以先选择开放，再按实际测试结果调整，不要求必须先通过生成测试才能保存。

模型从目录删除后，其遗留权限不应单独让模型重新可调用。配置界面应标明失效条目并允许清理，不能因为读取目录而自动补全或重写其他权限。

## 5. 后台交互

在统一配置界面增加“账号层级模型权限”矩阵：行是模型，列是 Free、Pro、Ultra 5x、Ultra 20x，以勾选框编辑。

- 支持按模型名称搜索、单模型全部层级勾选、按层级批量选择，以及将一个层级的权限复制到另一个层级。
- 复制是一次性的编辑动作，不建立持续继承关系。
- 展示新模型尚未授权、模型已从目录移除、全局隐藏等相关状态。
- 明确说明未知账号使用 Free 权限，Ultra 初始权限暂按 Pro 配置。
- 初始权限来源说明可放在帮助文本中，不把“管理员允许”展示成“上游已验证”。

账号列表保留现有层级和权益观察展示；可以提供查看该账号有效模型权限的入口，但第一版不增加单账号白名单覆盖，避免产生额外优先级。

## 6. 统一准入与调度

### 6.1 统一策略入口

建议在账号策略模块内提供通用判断，例如 `canUseModel(account, model, policy)`，返回是否允许，并能区分层级未知、未列入白名单等原因。具体接口名由实现确定。

所有入口使用同一模型规范化结果，包括协议前缀、已有别名、反截断前缀、思考等级、流式和工具后缀等现有转换。装饰后的名称不能绕过基础模型权限，不能另写一套不一致的字符串匹配。

`__files__` 等内部操作继续使用原有控制，不作为普通模型加入白名单；嵌入、图像、语音等已登记对外模型不能仅因类型不同而绕过权限。

### 6.2 最终可调度条件

```text
层级白名单允许
且账号在有效轮换范围内、健康、启用、未过期
且模型未被全局隐藏
且账号 × 模型未标记为不支持
且满足当前冷却、并发与上下文就绪要求
```

在候选账号筛选、租用、发送前最终检查以及重试换号时应用同一准入策略。覆盖调度模式与 legacy 模式；legacy 下也不能将受限模型发送给不允许的账号，若原有流程不能选择合格账号，应明确失败。

无账号拥有层级权限时，应尽早返回明确的“没有允许调用此模型的账号”错误，不进入无意义重试或持续排队。区分模型未登记、全局禁用、没有层级权限、账号暂时冷却或繁忙等原因；具体状态码沿用项目错误体系，新增稳定原因码用于前端和测试。

### 6.3 权限热更新

- 保存后原子替换运行时策略，清理候选缓存并触发队列和上下文池重新评估。
- 排队中和已经取得租用但尚未发送的请求重新检查权限；不符合时重新选账号或结束请求。
- 已经发出的上游请求正常完成，不因权限变更强制中断；后续重试使用最新权限。
- 修改账号层级也触发相同的重新评估。
- 不清空历史请求数、上游检测结果、不支持标记或冷却状态。

### 6.4 保留 Argon 的通道处理

替换的是 Argon 专用的本地层级门禁，不是它的全部运行逻辑。Argon 现有 MakerSuite 默认路由、权益上下文、真实认证、缓冲响应和超时处理继续保留。

其他模型被配置为仅付费可用，不代表它们应改走 MakerSuite，也不代表需要复制 Argon 的权益预检。传输通道配置、层级权限、额度估算分别管理。

## 7. 额度统计、上下文池与实际错误

### 7.1 统计

- 总额度和预计剩余额度只汇总对白名单允许的账号有意义的估算，不再仅为 Argon 过滤账号层级。
- 保持现有额度估算规则；本次不新增未经确认的具体额度，也不因为模型名中的 `pro` 推断准入。
- 不允许的账号不贡献该模型额度；允许但没有已知额度规则时继续显示未知，不能伪造为零或无限。
- 历史调用量继续保留；修改白名单只改变当前资格和额度口径，不抹除历史。
- 管理页、公示页采用相同口径，并区分层级允许账号数与当前可调度账号数。
- 估算剩余额度归零本身不新增调度拦截，继续沿用现有真实限流状态。

### 7.2 上下文池

判断账号是否仍有可服务模型时，只考虑该账号白名单允许且未全局隐藏的模型。不能因为存在一个账号无权调用的模型，就认定账号仍有可用服务能力。

无任何允许模型的账号不应为模型服务占用常驻池目标；有允许模型时继续结合现有健康、限流及冷却规则判断。不要把“无模型权限”写成“额度耗尽”。账号管理中的登录和权益检测仍可按原流程临时打开上下文。

### 7.3 上游错误

本地白名单只是管理员路由策略，上游仍可能因权益、区域、灰度或其他原因拒绝调用。

沿用并核对现有错误分类：明确属于账号模型不支持的结果保存在对应账号与模型状态中；不能把任意 `403` 都当成付费限制，也不能据单次调用失败自动修改全局层级白名单。管理员调整权限时不自动清除已有失败状态。

## 9. 实施顺序

1. 建立配置结构、统一模型规范化和准入函数，完成一次性初始化。
2. 接入候选筛选、租用、发送前校验及 legacy 路径，替换专用层级门禁。
3. 接入热更新、排队重评估、账号层级变更和上下文池协调。
4. 修正管理与公示统计，保留用量和运行状态。
5. 增加配置矩阵及新增模型的权限维护流程。
6. 完成必要回归测试与人工验收，更新运维说明。

第一版不增加单账号权限覆盖、自动模型探测、自动生成测试、通配符规则、自动学习层级权益或新的额度策略。

## 10. 验收标准

| 场景                                   | 预期结果                                                      |
| -------------------------------------- | ------------------------------------------------------------- |
| 首次初始化                             | 所有现有对外模型加入四层白名单，Free 仅移除三个已确认受限模型 |
| 未测试的现有模型                       | 初始可由 Free、Pro 和 Ultra 两档调用，不要求逐个测试          |
| Free 或未知账号请求三个受限模型        | 不向该账号发送；有合格账号则使用合格账号，否则返回明确原因    |
| Pro 和 Ultra 两档请求三个受限模型      | 本地层级准入通过，后续仍受真实权益与运行状态限制              |
| 重启或升级                             | 不覆盖已保存权限，不重新批量开放                              |
| 空白名单                               | 保持为空，不触发初始化或补全                                  |
| 配置非法                               | 保存失败且原有效配置保留；启动不静默全开放                    |
| 新增模型并选择允许层级                 | 只对选中层级开放                                              |
| 文件新增模型但没有权限配置             | 未授权，后台提示待配置                                        |
| 模型前缀、已有别名或请求修饰           | 使用同一基础模型的权限，无法绕过                              |
| 调度、legacy、重试换号                 | 全部执行相同层级门禁                                          |
| 修改权限或账号层级                     | 后续调度及发送前检查使用新策略，已发请求正常完成              |
| 层级权限变化后的统计                   | 资格及额度及时变化，历史用量、不支持和冷却状态保留            |
| 账号没有允许模型，或允许模型均不可服务 | 正确调整池资格，不被无权模型维持在常驻池中                    |
| 白名单允许但模型被全局隐藏             | 仍不可调用，白名单不覆盖全局禁用                              |
| Argon 回归                             | 原有认证、权益上下文、MakerSuite 通道和输出行为保持有效       |
| 普通上游 `403`                         | 不自动修改层级白名单，不一律判为模型权益不足                  |

测试重点是权限矩阵、迁移幂等、配置热更新、调度和非调度路径的一致性，以及额度与池资格联动。优先扩展现有账号层级、配置、调度、请求及 Argon 相关测试。

## 11. 实现与使用说明

### 11.1 配置保存与首次启动

- 配置键为 `MODEL_TIER_ALLOWLIST`，存于 `data/managed-config.json` 的 `overrides` 中，结构为本文定义的 `version: 1` 和四层 `tiers`。
- 首次启动且尚无此配置时，按当前 `configs/models.json` 生成初始权限并原子保存；之后重启或升级不重新扩充白名单。
- 可以使用同名环境变量提供首次初始化值，格式为完整 JSON；已保存的管理配置优先于后续环境变量变化。
- 权限矩阵不提供“恢复环境值 / 默认值”，避免重置时意外重新批量开放模型。需要撤销编辑时使用“放弃草稿”，需要修改已保存权限时显式勾选或清空。
- 无效版本、非法模型名称或损坏配置会报错，不静默全开放。模型已经从目录移除时，保留原有权限条目供管理员清理，但禁止实际调用。

### 11.2 日常维护

1. 打开控制台统一配置中的“账号层级模型权限”，点击默认折叠的“模型权限及启用设置”展开矩阵。
2. 按模型搜索，分别勾选 Free、Pro、Ultra 5x、Ultra 20x；可以按行勾选全部层级，也可以按列全选或清空。
3. 需要同步两个层级时，选择来源和目标并点击“复制层级权限”。这是草稿操作，不会持续绑定两者。
4. 点击页面“保存”使权限生效，无需为权限变更重启。未知账号按 Free 权限参与调度。

新增模型仍使用项目现有的文件目录维护方式：先在 `configs/models.json` 添加真实模型及元数据并重启，再进入权限矩阵选择允许的层级并保存。新模型显示“待授权”，可直接勾选全部层级后再按测试结果收紧。第一版没有另行增加模型元数据编辑器。

“清理失效条目”会从各层级草稿中移除已不在目录的模型，点击页面“保存”后生效。勾选层级白名单不会取消全局隐藏。

矩阵新增“是否启用”列，与控制台面板的“从面板移除／恢复显示”共用调度器状态及持久化，不引入另一套开关。勾选表示启用，取消表示全局隐藏并拒绝新请求，已发送请求正常完成。可以按模型修改，也可以搜索后点击“全部启用／全部禁用”批量修改当前搜索结果，再点击“应用启用状态”提交；这与页面“保存”层级权限是独立操作。部分提交失败时，成功项保留，失败项提示原因并保留以便重试；可点击“放弃启用状态修改”撤销未提交的启用状态草稿。

启用状态由后台定时读取，与面板操作同步；有层级权限草稿时也继续刷新启用状态，不覆盖权限草稿。legacy 模式下启用列及批量操作不可用，需先启用模型调度模式。

### 11.3 运行行为与验证

- 调度模式负责筛选合格账号；legacy 模式在当前账号不符合权限时明确失败，不将受限请求发送给该账号。
- 发送前读取当前有效权限，覆盖已排队、已租用未发送以及重试路径；已经发往上游的请求不会因修改权限而被主动中止。
- 无层级资格返回 `MODEL_TIER_DENIED`，未登记模型返回 `UNKNOWN_MODEL`，全局隐藏返回 `MODEL_DISABLED`；这些本地拒绝不作为上游权益或风控失败写入账号状态。
- 额度估算只汇总有权限的账号，历史请求数保留。管理页和公示页增加“层级允许”账号数，与当前可用账号数区分。
- 浏览器池区分权限为空、模型不支持与真实限流原因，权限恢复后重新评估候选和常驻目标。
- `tests/model-allowlist.test.js` 覆盖初始权限、未知层级、名称规范化、持久化、环境初始化、迁移幂等、新模型授权、非法配置、排队撤销、发送前复查、统计与池回收；配置页浏览器测试覆盖矩阵编辑、草稿放弃、保存及搜索。

验证命令：`npm test`、`npm run build:ui`，以及修改文件的 ESLint 和样式检查。测试使用本地桩和浏览器页面，不进行真实 Google 模型生成；Ultra 权限仍为按 Pro 初始化的暂定配置。
